Learning objectives

Build and execute a minimal clear/readback graph, explain consumer-first attachment and handle failed edits.

Libraries and headers

Initialize a native FArdaRHIDeviceRef, link Ardashir::ArdaRenderGraph, and include ArdaDependencyGraphNodes.h. The registry automatically installs upload, buffer-copy, clear, readback and synchronization definitions. CUDA adapters are in ArdaDependencyGraphCuda.h.

Clear and read back three frames

#include "ArdaDependencyGraphNodes.h"
using namespace arda;
FArdaRHIStatus Run(FArdaRHIDeviceRef Device)
{
    FArdaDependencyGraph Graph(Device);
    if (auto S = Graph.BeginGraphEdit(); !S) return S;
    FArdaRHIBufferDesc Desc;
    Desc.mByteSize = 256;
    Desc.mUsage = EArdaRHIBufferUsage::UnorderedAccess;
    auto Output = Graph.CreateBuffer("output", Desc);
    if (!Output) return Output.mStatus;
    auto Bytes = eastl::make_shared<eastl::vector<uint8_t>>();
    auto Read = Graph.AttachOrFind("read", "arda.readback",
        FArdaGraphReadbackParameters{Output.mValue, Bytes});
    if (!Read) return Read.mStatus;
    auto Clear = Graph.AttachOrFind("clear", "arda.clear-buffer",
        FArdaGraphClearParameters{Output.mValue, 7});
    if (!Clear) return Clear.mStatus;
    if (auto S = Graph.EndGraphEdit(); !S) return S;
    for (unsigned Frame = 0; Frame != 3; ++Frame)
    {
        auto Result = Graph.Execute();
        if (!Result.mStatus) return Result.mStatus;
        // Bytes holds 64 uint32_t values, each equal to 7.
    }
    return {};
}

Parameters belong to each node

Every node class declares its own FArdaParameters struct with only that operation's inputs and outputs. Each attached instance owns an immutable snapshot, so changing a local parameter value cannot change another node or graph. Pass a prefilled struct, an inline aggregate, or a callback that fills a fresh struct during attachment:

// Inside BeginGraphEdit / EndGraphEdit, after declaring the destination buffers.
FArdaGraphClearNode::FArdaParameters ClearParameters;
ClearParameters.mDestination = FirstBuffer;
ClearParameters.mValue = 7;
auto First = Graph.AttachOrFind<FArdaGraphClearNode>("clear first", ClearParameters);
if (!First) return First.mStatus;

auto Second = Graph.AttachOrFind<FArdaGraphClearNode>("clear second",
    [&](FArdaGraphClearNode::FArdaParameters& Parameters)
    {
        Parameters.mDestination = SecondBuffer;
        Parameters.mValue = 42;
    });
if (!Second) return Second.mStatus;

The callback runs synchronously once per attachment call, including reattachment, before validation or preparation. It can return FArdaRHIStatus to reject initialization. Do not retain its temporary reference or edit the graph inside it. Resource declaration fills omitted node-owned outputs before parameters are frozen. Deliberately shared resource or dynamic input pointees keep their documented lifetime and synchronization requirements; copying the parameter struct does not deep-copy them.

Migration: texture-to-buffer and buffer-to-texture nodes now have distinct FArdaGraphTextureToBufferParameters and FArdaGraphBufferToTextureParameters structs. Prefer Node::FArdaParameters at attachment sites. Cornell Box, PixelSort and triangle examples likewise use a separate schema for each node.

Consumer-first attachment

The readback reads the value produced by clear, so compilation orders clear first. Readback is observable and retains its producer. Use MarkOutput() for a graph-owned output without another observable consumer. Imported and persistent outputs are also roots.

Change semantics through edits

AttachOrFind() reuses a name only when definition and canonical key match. Replace changed operations within an edit. Removing a producer also removes resource-dependent consumers, which must be recreated as needed. Failed compilation leaves the edit open for repair or CancelGraphEdit().

Check every result

Invalid handles, uncovered reads, contradictory dependencies, cycles and ambiguous pipelines fail compilation. For repeated writes to an overlapping region, attach writers and intervening readers in their intended order; the resource example shows which contents each read observes. Regions with one producer still allow readers to be attached first. Native recording, submission and completion failures propagate through execution status. GPU work already accepted by a queue cannot be rolled back.

Chapter summary

Readback makes the clear output observable; a single successful edit produces the plan reused by all three executions.
