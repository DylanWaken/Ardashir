One faithful graph, end to end

Getting started

A first integration follows one disciplined sequence: initialize ArdaBackend, derive an ARDG context, construct one builder, declare logical resources and immutable pass parameters, register passes, make outputs observable, compile or execute once, synchronize where required, and release graph-dependent objects before backend shutdown.

Learning objectives

After this chapter, you should be able to:

  • include the aggregate public header and derive graph execution context from a live backend context;
  • explain which objects the builder owns and which objects remain caller- or backend-owned;
  • declare resource access through generated standard-layout parameter metadata;
  • create graph-owned logical resources and register external physical resources with truthful initial states;
  • register a callback that obtains declared physical resources through the pass execution context;
  • choose extraction for a retained result or external import/final state for presentation;
  • compile explicitly for inspection or rely on compile-on-demand during one execution;
  • separate CPU submission success from GPU completion; and
  • tear down graph, extracted, presentation, and backend objects in safe order.

Prerequisites

Read the overview and complete ArdaBackend initialization. You need a valid backend::FArdaDeviceContext whose device remains alive through graph execution. Review ownership, command lists, queues, resource states, and extraction.

At build time, link the ArdaRenderGraph target and its ArdaBackend dependency. The public include directory is Source/ArdaRenderGraph/Public; consumers normally include the aggregate header rather than private compiler or executor headers.

Mental model: describe, lower, submit

Treat the builder as a short-lived compiler object for one GPU workload:

  1. Describe. Logical resources and frozen parameters form an intermediate representation. A logical resource is a name and descriptor plus graph history, not necessarily a physical allocation.
  2. Lower. Compilation turns declarations into a live pass sequence, inclusive resource intervals, per-pass transitions, pipeline choices, cross-queue dependencies, and raster-group metadata.
  3. Submit. Execution materializes physical backing, rebuilds state against actual physical identities, records command lists, inserts waits, submits, and publishes retained outputs.

This separation is the transferable compiler idea behind render graphs: author semantic intent in a high-level representation, validate it while the whole program is visible, then lower it to a target execution model.

Step 1: include the public surface and derive context

Source/ArdaRenderGraph/Public/ArdaRenderGraph.h aggregates definitions, resources, parameters, passes, blackboard, builder, and the bridge from ArdaBackend. Its MakeRenderGraphContext() helper copies the retained device reference and the backend's actual graphics, compute, and copy queue capabilities.

#include "ArdaBackend.h"
#include "ArdaRenderGraph.h"

using namespace arda;

const backend::FArdaDeviceContext& deviceContext =
    backend::GetDeviceContext();

render_graph::FARDGRenderGraphContext graphContext =
    render_graph::MakeRenderGraphContext(deviceContext);

The resulting FARDGRenderGraphContext retains the RHI device. It also stores queue capabilities and optional debug behavior. Do not hard-code compute or copy support: the compiler uses these bits to decide whether eligible passes remain on a specialized queue or fall back to graphics.

Graphics capability is mandatory

The builder constructor performs a fatal check if the graph context lacks graphics capability. Prologue, epilogue, fallback, uniform upload, and ordinary graphics work rely on that baseline.

Step 2: create one builder and assign ownership

Construct FARDGBuilder after all long-lived objects captured by pass callbacks exist. The builder is non-copyable and non-movable because its private arena, registries, stable pointers, mutex, and execution state have one identity.

render_graph::FARDGBuilder graph(graphContext);
Builder-owned
Logical records, copied or allocated parameters, pass callbacks, compile products, physical references bound during execution, extraction declarations, and blackboard values.
Caller-owned
The builder itself, output reference variables supplied for extraction, objects captured by reference in callbacks, and external presentation or imported-resource policy.
Retained but externally created
The RHI device in the graph context and RHI references passed to external registration. Retention keeps objects alive but does not transfer conceptual ownership.
GPU-effective lifetime
Submitted work may continue after Execute() returns. Command submission retains required resources under the RHI contract, but CPU-visible reuse and external destruction still require explicit completion reasoning.

Keep the builder on one setup thread. Current public mutation methods do not promise concurrent graph construction. Parallelism occurs later during command-list recording, where each eligible pass owns a distinct command list and the execution context guards physical access.

Step 3: declare parameters and logical resources

Parameter structs are executable contracts

ARDG_BEGIN_PARAMETER_STRUCT and ARDG_END_PARAMETER_STRUCT generate a standard-layout C++ type plus immutable metadata. Resource macros contribute member offset, size, alignment, element count, semantic type, and default state. At pass registration, ARDG recursively visits leaves in declaration order to derive accesses and edges.

ARDG_BEGIN_PARAMETER_STRUCT(FClearParameters)
    ARDG_BUFFER_ACCESS(mOutput)
ARDG_END_PARAMETER_STRUCT()

ARDG_BUFFER_ACCESS uses FARDGBufferAccess, so setup supplies both the logical buffer and its required state. Direct access is appropriate when the pass operates on the parent buffer and does not need a logical SRV or UAV descriptor.

Create a graph-owned logical resource

rhi::FArdaRHIBufferDesc outputDesc;
outputDesc.mDebugName = "GettingStarted.Output";
outputDesc.mByteSize = 1024;
outputDesc.mStructureStride = sizeof(uint32_t);
outputDesc.mUsage =
    rhi::EArdaRHIBufferUsage::Structured |
    rhi::EArdaRHIBufferUsage::UnorderedAccess;

render_graph::FARDGBufferRef output =
    graph.CreateBuffer(outputDesc);

CreateBuffer() validates a non-empty name and nonzero size, appends a logical record to the buffer registry, and returns a raw graph-owned pointer. The default resource flag is transient. The call does not create an RHI buffer; materialization happens only for live resources during execution.

Allocate stable parameter storage

FClearParameters* parameters =
    graph.AllocateParameters<FClearParameters>();
parameters->mOutput.mBuffer = output;
parameters->mOutput.mState =
    rhi::EArdaRHIResourceState::UnorderedAccess;

AllocateParameters() constructs the object in graph arena storage and registers a destructor when needed. Passing a stack parameter object to AddPass is also supported. The private FreezeParameters implementation helper is invoked automatically by AddPass and CreateUniformBuffer to copy caller-owned parameters into immutable arena storage when needed; it is never a user-callable step. Later mutations to the original stack object do not change the pass.

Step 4: register the pass

Register producers before consumers. AddPass() appends the pass first, then visits the frozen parameters. That stable, later handle allows resource history to point from existing producers and readers toward the new pass.

graph.AddPass(
    "ClearOutput",
    parameters,
    render_graph::EARDGPassFlags::Compute,
    [](render_graph::FARDGPassExecutionContext& context,
       const FClearParameters& frozen)
    {
        rhi::IArdaRHIBuffer* physical =
            context.GetBuffer(frozen.mOutput.mBuffer);
        context.mUnsafeRawCommandList.ClearBufferUInt(
            *physical,
            0x12345678u);
    });

The callback runs during command recording, not registration. The GetBuffer() call verifies that the logical buffer belongs to this graph, has physical backing, is declared by this pass, and is requested while this pass's access gate is open. The raw command list performs the operation, but the graph resource is obtained through the validated context.

Pass flags are constraints

EARDGPassFlags identifies raster, compute, async-compute, copy, never-cull, render-pass, and parallel-recording behavior. Illegal combinations are fatal. AsyncCompute requires Compute; SkipRenderPass requires Raster; raster, copy, and compute categories cannot be combined arbitrarily.

When to add a manual dependency

Resource declarations derive most dependencies. Use AddDependency() only for real causality not represented by a resource, such as an externally visible side effect. Both handles must already exist and the producer handle must precede the consumer. A manual dependency participates in both ordering and culling reachability.

Step 5: choose an output workflow

Workflow A: extract a graph-created result

Extraction makes a graph-created resource observable, keeps it live through the epilogue, removes transient eligibility, requests a known final state, and assigns a retained RHI reference after submission.

rhi::FArdaRHIBufferRef extractedOutput;
graph.QueueBufferExtraction(
    output,
    extractedOutput,
    rhi::EArdaRHIResourceState::CopySource);

The address of extractedOutput is stored until execution. It must remain valid and uniquely associated with this extraction. QueueBufferExtraction() rejects nulls, foreign graph records, unknown final states, duplicate resources, and duplicate output addresses with fatal checks.

Workflow B: render to an external presentable image

A swap-chain image is already physical and externally owned. Register it with its truthful current state—normally Present at graph entry—then declare it in a raster pass and leave its final state as Present:

render_graph::FARDGTextureRef backBuffer =
    graph.RegisterExternalTexture(
        acquiredTexture,
        rhi::EArdaRHIResourceState::Present,
        "BackBuffer");

// In a raster parameter struct:
// ARDG_RENDER_TARGET_BINDING_SLOTS(mRenderTargets)
// parameters->mRenderTargets.mColor[0].mTexture = backBuffer;

backBuffer->SetFinalState(
    rhi::EArdaRHIResourceState::Present);

RegisterExternalTexture() retains the RHI texture, marks it external, sets the prologue as its initial producer, and deduplicates repeated registration by physical identity when the initial states agree. Writes to an external resource become observable through the epilogue, so they root the required producer chain. After graph submission, the application's normal swap-chain workflow presents the image; ARDG does not own acquisition, presentation, resize, or frame pacing.

Never guess an imported state

The graph cannot reconstruct commands issued before import. A wrong initial state makes later transition derivation start from false history. Coordinate the state contract with the external owner and register one consistent state for each physical identity.

Worked example: create, clear, extract, submit

The following function assumes ArdaBackend is already initialized. It creates one structured buffer, clears it in a compute pass, extracts it in copy-source state, submits the graph, and waits before returning the buffer for CPU-coordinated follow-up work.

ARDG_BEGIN_PARAMETER_STRUCT(FClearParameters)
    ARDG_BUFFER_ACCESS(mOutput)
ARDG_END_PARAMETER_STRUCT()

arda::rhi::FArdaRHIBufferRef BuildClearGraph(
    const arda::backend::FArdaDeviceContext& deviceContext)
{
    using namespace arda;
    using namespace render_graph;

    FARDGBuilder graph(MakeRenderGraphContext(deviceContext));

    rhi::FArdaRHIBufferDesc desc;
    desc.mDebugName = "GettingStarted.Output";
    desc.mByteSize = 1024;
    desc.mStructureStride = sizeof(uint32_t);
    desc.mUsage =
        rhi::EArdaRHIBufferUsage::Structured |
        rhi::EArdaRHIBufferUsage::UnorderedAccess;

    FARDGBufferRef output = graph.CreateBuffer(desc);
    FClearParameters* parameters =
        graph.AllocateParameters<FClearParameters>();
    parameters->mOutput = {
        output,
        rhi::EArdaRHIResourceState::UnorderedAccess,
        {}};

    graph.AddPass(
        "ClearOutput",
        parameters,
        EARDGPassFlags::Compute,
        [](FARDGPassExecutionContext& context,
           const FClearParameters& frozen)
        {
            context.mUnsafeRawCommandList.ClearBufferUInt(
                *context.GetBuffer(frozen.mOutput.mBuffer),
                0x12345678u);
        });

    rhi::FArdaRHIBufferRef extracted;
    graph.QueueBufferExtraction(
        output,
        extracted,
        rhi::EArdaRHIResourceState::CopySource);

    FARDGExecuteOptions options;
    options.mbParallelRecording = false;
    const FARDGExecutionResult& result = graph.Execute(options);
    (void)result; // Record counters and submitted instances in production.

    // This simple boundary waits before returning CPU-coordinated ownership.
    // A frame renderer would normally use submitted instances asynchronously.
    if (!deviceContext.mDevice->WaitForIdle())
        return nullptr;

    return extracted;
}

Why every line exists

  1. The generated parameter metadata tells setup that the pass writes the buffer in unordered-access state.
  2. The descriptor's usage permits the clear operation; the logical descriptor also drives physical materialization.
  3. The parameter allocation gives the callback stable immutable storage through recording.
  4. The execution-context getter proves that the requested buffer was declared for this pass.
  5. Extraction gives culling an observable root and requests the state needed by follow-up copy or readback work.
  6. Disabling parallel recording is unnecessary for one pass but makes the first example's CPU behavior simple. Production code can keep the default.
  7. The explicit idle wait is intentionally conservative. It converts submission into completion before the reference crosses this function's CPU coordination boundary.

Step 6: compile for inspection, then execute once

You may call Compile() explicitly before execution:

const render_graph::FARDGCompileResult& plan = graph.Compile();
const eastl::string report = graph.DumpGraph();

const render_graph::FARDGExecutionResult& submitted =
    graph.Execute();

This is useful for deterministic diagnostics, plan inspection, and tests. Repeated compile calls return the same builder-owned result. Execute() calls compile automatically when needed, so explicit compilation is optional.

What compilation establishes

  • all declarations pass pre-compile validation, including read-before-produce and queue-state legality;
  • the epilogue is appended and observable producer chains are rooted;
  • execution order is the live registration-order subsequence;
  • resource lifetimes, logical transitions, queue dependencies, async fork/join metadata, and raster groups are stable.

What execution establishes

  • live resources were materialized or verified as external;
  • runtime transitions were rebuilt against physical identities;
  • pass command lists and any epilogue transition list were recorded and submitted;
  • required cross-queue waits were issued and extraction outputs were assigned;
  • the builder is terminally executed and cannot execute again.

What execution does not establish

It does not establish that graphics, compute, or copy queues have completed. FARDGExecutionResult reports submission counters, pool behavior, debug behavior, and the last submitted instance per queue. Use those values with backend completion mechanisms instead of assuming the CPU return point is a GPU fence.

Step 7: clean up in dependency order

The builder destructor releases graph-scoped registries, callbacks, frozen parameters, blackboard values, and held physical references. Arena destructors run in reverse construction order before backing blocks are freed. That CPU cleanup is independent from GPU retirement.

Per-frame or per-workload cleanup

  1. Submit the graph once.
  2. Move or copy required extracted RHI references into their next owner.
  3. Preserve any completion instances required by frame-resource retirement.
  4. Let the builder leave scope; never retain its logical pointers, handles, parameter pointers, blackboard references, or compile-result references.
  5. Release extracted references only after both application use and required GPU use have ended.

Application shutdown

  1. Stop scheduling new graphs and join setup or recording producers.
  2. Wait for relevant submitted GPU instances or device idle.
  3. Destroy builders, swap chains, extracted resources, caches, and renderer systems.
  4. Release retained device references derived into graph contexts.
  5. Shut down ArdaBackend last.

Captured references are your contract

Pass callbacks are stored until execution. Values captured by copy must be copyable and valid for recording; references and pointers captured by reference must outlive every callback invocation, including worker-thread recording. Prefer graph parameters for graph resource declarations and narrow value captures for non-resource setup.

Threading, platform, and performance notes

Setup thread
Build the graph serially unless a future API explicitly documents concurrent mutation. Append-only registries provide stable identity, not a concurrent writer contract.
Recording workers
Execution groups passes into dependency levels. Eligible passes at one level may record through std::async, bounded by mMaxRecordingThreads. Each pass writes a distinct command list and result slot.
Serial exceptions
Immediate mode, disabled parallel recording, and NeverParallel force serial recording. Use NeverParallel when callback-side non-graph state cannot safely be accessed concurrently.
Submission order
Submission remains deterministic in execution order even if CPU recording completes out of order. Cross-queue producer instances become wait tokens for consumers.
Platform boundary
ARDG code is backend-neutral. D3D12/Vulkan behavior, native queues, and presentation surfaces stay below Arda RHI and ArdaBackend.
Transient resources
Current execution can reuse exact committed-resource matches across non-overlapping lifetimes in one queue domain. It does not apply physical placed-memory aliasing.
Debug modes
Immediate mode, conservative barriers, extended lifetimes, and first-write clobbering are correctness tools. They deliberately trade performance or normal scheduling for diagnostic clarity.

Failure modes: symptom, cause, prevention, recovery

Fatal check at builder construction
Symptom: “requires graphics queue capability.” Cause: an incomplete or fabricated context. Prevention: use MakeRenderGraphContext with a live backend context. Recovery: correct backend initialization and rebuild the graph.
Fatal check while creating a resource
Symptom: invalid logical declaration. Cause: empty debug name, zero dimensions/size, or illegal ownership flags. Prevention: fully initialize RHI descriptors and use registration—not creation—for external objects. Recovery: correct the descriptor before adding passes.
Pass is culled
Symptom: callback never records. Cause: no path to an observable root. Prevention: model the real external write or extraction. Recovery: inspect DumpGraph(); use NeverCull only for a genuine side effect.
Fatal check during compile
Symptom: read-before-produce, conflicting states, or illegal queue state. Cause: declarations describe an impossible program. Prevention: define every input source and one compatible state per resource unit in a pass. Recovery: repair parameters and pass order, then build a fresh graph if execution had started.
Fatal check during callback
Symptom: unavailable or undeclared graph resource. Cause: wrong graph, wrong exact view, omitted parameter, or access outside the active callback. Prevention: route graph resources through frozen parameters and context getters. Recovery: correct the declaration; do not retain raw logical pointers beyond the builder.
Extracted reference is null
Symptom: no output after expected work. Cause: execution did not complete its CPU submission path or an earlier fatal failure made the builder terminal. Prevention: queue extraction during build and keep output storage alive. Recovery: discard the failed builder and diagnose the first failure.
Stale or corrupted CPU readback
Symptom: extracted object exists but contents are not ready. Cause: submission was mistaken for completion. Prevention: synchronize with the relevant RHI queue instance or use a device wait at a conservative boundary. Recovery: wait before access and audit external lifetime.

Production integration checklist

  • ArdaBackend and the device outlive every builder and submitted graph dependency.
  • ArdaRenderGraph.h is used; no private compiler, executor, registry, or allocator header leaks into consumers.
  • Graph context comes from the live device context, including actual queue capabilities.
  • One builder represents one workload and executes at most once.
  • Passes are registered in producer-before-consumer order.
  • Every resource access is present in generated parameter metadata with a truthful state and range.
  • Graph-created descriptors have non-empty diagnostic names and valid usage flags.
  • External resources have a known, coordinated initial state and remain externally valid.
  • Each required output is an external write, extraction, or deliberate never-cull side effect.
  • Extraction output locations remain valid and unique through execution.
  • Pass callbacks use execution-context getters for graph resources.
  • Raw command-list use does not smuggle undeclared graph resources into callbacks.
  • Reference captures are safe under possible parallel recording, or the pass is deliberately NeverParallel.
  • Compile dumps and execution counters are retained in diagnostic builds.
  • GPU completion is established before CPU readback or externally constrained destruction/reuse.
  • Logical pointers, handles, parameter pointers, and blackboard references never outlive the builder.
  • Graphs and renderer-held RHI references are released before backend shutdown.

Chapter summary

  • Use the aggregate header and derive context from the initialized backend rather than fabricating capabilities.
  • The builder owns logical graph state and frozen parameters; callers own external objects, extraction destinations, and backend lifecycle.
  • Parameter metadata is the dependency, state, and physical-access contract for a pass.
  • Extraction retains a graph-created result; external import plus a final Present state supports swap-chain workflow.
  • Compilation is cached, execution is one-shot, and successful execution means submission rather than GPU completion.
