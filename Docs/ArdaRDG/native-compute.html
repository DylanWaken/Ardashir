Write a native compute node

Give an operation one ID, one resource contract and one list of implementations. A renderer or graph node can then run it on the current device without choosing a kernel itself.

What the caller owns

The caller supplies the resources and scalar values for an invocation. The operand defines what the operation does. The provider owns the compiler, argument ABI and handoff to its execution queue. Keep the registry for as long as you need to prepare new invocations.

Register a buffer fill

This example writes the numbers 0 through 15 into a 64-byte buffer. Link Ardashir::ArdaNativeCompute to your application. For this CUDA C++ implementation, build with ARDASHIR_ENABLE_CUDA=ON and an NVRTC-enabled CUDA Toolkit. Initialize the graphics device with an available CUDA execution mode.

At startup, register CreateArdaNativeCudaInGraphicsProvider() and CreateArdaNativeCudaProvider() with registry.RegisterProvider. Check each status. The example shares one source between the CiG and general CUDA variants. Each operand declares its views in the order callers must bind them. For this kernel the pointer occupies eight bytes in the argument block. The patch tells CUDA to put the address of resource slot 0 at byte offset 0.

#include "ArdaNativeCompute.h"
#include "CUDA/ArdaNativeCudaProvider.h"
using namespace arda;

FArdaRHIStatus RegisterFill(FArdaNativeComputeRegistry& registry,
    FArdaNativeShaderFallback fallback = {})
{
    FArdaNativeCudaSourceDesc source;
    source.mCudaCpp = R"(
        extern "C" __global__ void fill(unsigned int* output) {
            output[threadIdx.x] = threadIdx.x;
        }
    )";
    source.mModuleKernel.mEntryPoint = "fill";
    source.mModuleKernel.mParameterSize = 8;
    source.mModuleKernel.mParameterAlignment = 8;
    source.mModuleKernel.mArguments = {{0, 8, 8, EArdaCudaModuleArgumentKind::Buffer}};
    source.mPatches = {{0, 0, alignof(uint32_t)}};
    auto kernel = CreateArdaNativeCudaSource(eastl::move(source));
    if (!kernel) return kernel.mStatus;

    FArdaNativeOperandDesc fill;
    fill.mId = "example.fill16";
    fill.mResources = {{"output", EArdaRHIResourceType::Buffer, EArdaComputeAccess::Write}};
    fill.mParameterSize = 8;
    fill.mFallback = eastl::move(fallback);
    fill.mValidate = [](const FArdaNativeInvocation& call) {
        const auto& range = call.mResources[0].mBufferRange;
        const auto& buffer = dynamic_cast<const IArdaRHIBuffer&>(*call.mResources[0].mResource);
        if (range.Resolve(buffer.GetDesc()).mByteSize < 16 * sizeof(uint32_t))
            return FArdaRHIStatus::Error(EArdaRHIResult::InvalidArgument, "fill16 needs 64 bytes.");
        return FArdaRHIStatus{};
    };
    AddArdaNativeCudaVariants(fill, {"fill16", kernel.mValue,
        [](const FArdaNativeComputeContext&, const FArdaNativeInvocation&) {
            FArdaNativeLaunch launch;
            launch.mBlockSize[0] = 16;
            return TArdaRHIResult<FArdaNativeLaunch>{launch, {}};
        }});
    return registry.RegisterOperand(eastl::move(fill));
}

Record and submit

Pass a device-local buffer created with mbCudaInterop = true and concrete usage flags such as UnorderedAccess. Prepare the operand with the device and queue of the command list that will record it. The plan owns the selected work. The RHI keeps its submitted resources alive until the GPU finishes.

TArdaRHIResult<uint64_t> RunFill(const FArdaNativeComputeRegistry& registry,
    FArdaRHIDeviceRef device, FArdaRHIBufferRef output)
{
    FArdaNativeComputeContext context{device, EArdaRHIQueueType::Graphics};
    FArdaNativeInvocation call;
    call.mResources.push_back({output, {0, 64}});
    call.mParameters.resize(8, 0);

    auto plan = registry.Prepare("example.fill16", context, call);
    if (!plan) return {{}, plan.mStatus};
    auto list = device->CreateCommandList(context.mQueue);
    if (!list) return {{}, list.mStatus};
    if (auto s = list.mValue->Open(); !s) return {{}, s};
    if (auto s = list.mValue->RecordNativeCompute(plan.mValue); !s) return {{}, s};
    if (auto s = list.mValue->Close(); !s) return {{}, s};
    return device->ExecuteCommandList(list.mValue);
}

The return value identifies the submission. To inspect the values on the CPU, record CopyBufferDeviceToHost after the dispatch and before closing the list. This synchronous copy fills the destination byte vector before ExecuteCommandList returns. For a submission without a synchronous readback, WaitForSubmission(token) waits for completion. CUDA orders its access to the buffer with the surrounding graphics commands. D3D12 Compute in Graphics requires a graphics queue. CUDA synchronization and allocation

Choose a CUDA source

Set one source on FArdaNativeCudaSourceDesc. A module entry needs the exported symbol, ordered arguments, storage size and alignment. Resource patches map those arguments to operand slots. Keep these declarations beside the kernel or generate them from the same parameter schema used to build it.

Select a variant or a shader

Put the most specialized kernel first. The registry checks the device, graphics API, provider, source format and architecture. The variant's mSelect callback can use input shape or layout to choose launch dimensions. Return Unsupported when another variant should handle the input. Use the operand's mValidate for input errors common to every implementation.

A nonshared texture has two common routes. A shader can use the original allocation if it has the required view and usage flags. For a CUDA surface kernel, allocate a compatible shareable texture and bind that mip. Copy into it before a read, copy back after a write if the original texture needs the result, and do both for an in-place update. A kernel that accepts a buffer pointer can instead use pitched texture-to-buffer copies. The kernel and operand must agree on that representation. Pitched copies in a graph

Supply a shader implementation on the same operand. For the buffer fill, create a compute pipeline for the shader below with one raw buffer UAV at slot 0. Create the buffer with Raw | UnorderedAccess usage to support the shader route. The shader writes the same 16 values as the CUDA kernel.

RWByteAddressBuffer output : register(u0);
[numthreads(16, 1, 1)]
void FillCS(uint lane : SV_GroupIndex)
{
    output.Store(lane * 4, lane);
}

Once you have the pipeline and its owning device, pass this fallback to RegisterFill. The binding set uses the caller's exact buffer range. The returned work captures the pipeline and set so they survive preparation.

FArdaNativeShaderFallback MakeFillFallback(FArdaRHIDeviceRef device,
    FArdaRHIComputePipelineRef pipeline)
{
    FArdaNativeShaderFallback fallback;
    fallback.mPrepare = [device, pipeline](const FArdaNativeComputeContext& ctx,
        const FArdaNativeInvocation& call) -> TArdaRHIResult<FArdaNativeWorkRef> {
        if (ctx.mDevice != device)
            return {{}, FArdaRHIStatus::Error(EArdaRHIResult::WrongDevice, "Fill pipeline belongs to another device.")};
        FArdaRHIBindingSetDesc desc;
        desc.mLayout = pipeline->GetDesc().mBindingLayouts.front();
        desc.mItems.push_back({0, 0, EArdaRHIBindingType::RawBufferUAV, call.mResources[0].mResource});
        desc.mItems[0].mView.mBufferRange = call.mResources[0].mBufferRange;
        auto set = device->CreateBindingSet(desc);
        if (!set) return {{}, set.mStatus};
        FArdaRHIComputeState state{pipeline, {set.mValue}};
        return {MakeArdaNativeWork([state](IArdaRHICommandList& list) {
            if (auto s = list.SetComputeState(state); !s) return s;
            list.Dispatch(1, 1, 1);
            return FArdaRHIStatus{};
        }), {}};
    };
    return fallback;
}

For a raster implementation, set the route to GraphicsShader, declare its required features and return work that sets graphics state and draws. PixelSort shows input-dependent selection in a full application. It picks a column kernel for portrait images and a row kernel otherwise. Its shader sorts the same tiles. CheckSupport can rule out unavailable routes before creating resources. Prepare also checks the actual views and inputs and can try another variant after a compilation failure. The plan fixes the route before the first command. A recording or submission error returns to the caller so a partially recorded operation cannot execute twice. Support query · Preparation

Call the operand from a graph

Declare the node's resource access so the graph can schedule the producers and consumers. In the recording callback, resolve those handles to RHI views in operand slot order and pass the invocation to the execution context. The context checks the requested views against the node's declarations. It records into the graph's command list and leaves submission to the graph.

FArdaNativeInvocation call;
call.mResources.push_back({context.GetBuffer(outputHandle), {0, 64}});
call.mParameters.resize(8, 0);
return context.RecordNativeCompute(registry, "example.fill16", call,
    EArdaNativeComputePreference::PreferNative);

The graph checks the pass declarations before the registry prepares each candidate. For example, CUDA needs unordered-access state for a shared buffer. A pass that declares a shader-resource read can use a compute fallback that reads through an SRV. Every route still needs permission to access the full bound range.

A CUDA sequence can share one graphics-to-CUDA handoff across several nodes. In a PrepareCuda callback, append with AppendNativeCudaCompute. An explicitly batched CUDA pass accepts only CUDA work. Before building that pass or allocating shared textures, call CheckSupport with mPreference = NativeOnly and mAllowedProviderIds = {ArdaNativeCudaInGraphicsProviderId, ArdaNativeCudaProviderId}. To require CiG, set mRequiredProviderId = ArdaNativeCudaInGraphicsProviderId. Frame inputs must still satisfy the chosen kernel. Add a compute provider

Implement IArdaNativeComputeProvider in a target that links Ardashir::ArdaNativeCompute. Keep SDK headers, compiler options, source layout and native synchronization in the provider or its graphics backend integration. An application registers the provider and can add one of its sources to any compatible operand.

  1. Return a stable provider ID, supported graphics module names and loadable source formats from GetDesc. Give each source an owning IArdaNativeKernelSource with the same provider ID and a format from that list.
  2. Use CheckSupport to qualify the device, queue, architecture and operand schema. The registry calls it during preflight, before there are any frame resources.
  3. In QueryHandoff, inspect the allocation and view. For direct access, return Direct and the RHI state the view must have on entry. Return ConversionRequired when a different representation can satisfy the kernel, or an error explaining why the provider cannot use it.
  4. Implement Prepare to resolve the source and freeze argument values and resource references. Return a work object whose Record appends commands to the caller's list.

If your compute library needs a new native command, define an IArdaRHINativeOperation payload. In each supported graphics backend, advertise the operation ID through SupportsNativeOperation and implement IArdaProviderCommandList::RecordNativeOperation. Check the device for that ID during preflight so a device without the integration can select a fallback.

Inside your prepared work, call commands.RecordNativeOperation(desc) with the payload and its ordered views. The backend receives the native buffer or texture objects and resolved ranges. It owns synchronization with the external queue and retains the packet until execution retires. Record an operation on the RHI list · Implement a graphics backend recorder

Return Unsupported for a missing capability and InvalidArgument for malformed data. A compiler or backend failure during preparation can fall through to another implementation. Once recording starts, propagate the first error. Provider and operand API reference

Verify a launch

Build the native module tests and run the registry and CUDA cases. The GPU tests write a buffer subrange and check the sentinel on both sides after readback. They cover CUDA C++ and imported PTX on each linked graphics backend. For D3D12 vendor intrinsics or a device that requires CiG, see Choose a GPU provider. The PixelSort tests compare the sorted image with a CPU result, including partial tiles.

cmake --build build --target ArdaNativeComputeTests
ctest --test-dir build -R ArdaNative --output-on-failure
