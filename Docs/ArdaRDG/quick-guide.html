Renderer quick guide

Attach registered operations, wire logical outputs, compile once and execute repeatedly.

Learning objectives and prerequisites

Learn the renderer-facing composition model. Start with graph edit lifetime and frozen parameters. For complete class definitions and all pipeline families, use the node recipes.

Library setup and ownership

A node class contains its own shader registration, parameter schema, output declaration and execution hook. The common base handles type registration and shared immutable preparation. A node declares its hardware and environment needs through static GetRequirements; unsupported attachment fails before its output declaration or preparation. See feature admission and failure handling. The renderer does not create binding layouts or binding sets. The graph generates layouts from shader metadata, allocates declared outputs, infers PSOs and prepares per-frame descriptor tables and shader tables at compilation.

Call MyNode::Register() to populate the singleton registry for discovery before graph use. Typed AttachOrFind<MyNode> also registers automatically. Include each class header and link its implementation; do not duplicate its shader registration in the renderer.

Compose operations

This complete assembly uses the compiled compute recipe. The operation declares its output automatically. Readback is a separate consumer, so its resource edge determines order. Retain the graph as renderer state instead of reconstructing it for each frame.

FArdaRHIStatus RunComputeRecipe(FArdaRHIDeviceRef Device)
	{
		FArdaDependencyGraph Graph(Device);
		if (auto S = Graph.BeginGraphEdit(); !S)
		{
			return S;
		}
		auto Compute = Graph.AttachOrFind<FArdaComputeWriteNode>("write", {{}, 123});
		if (!Compute)
		{
			return Compute.mStatus;
		}
		auto Bytes = eastl::make_shared<eastl::vector<uint8_t>>();
		auto Read =
		    Graph.AttachOrFind<FArdaGraphReadbackNode>("read", {Graph.FindOutput(Compute.mValue, "Output"), Bytes});
		if (!Read)
		{
			return Read.mStatus;
		}
		if (auto S = Graph.EndGraphEdit(); !S)
		{
			return S;
		}
		for (unsigned Frame = 0; Frame < 3; ++Frame)
		{
			const auto Run = Graph.Execute();
			if (!Run.mStatus)
			{
				return Run.mStatus;
			}
			uint32_t Value = 0;
			if (Bytes->size() != sizeof(Value))
			{
				return FArdaRHIStatus::Error(EArdaRHIResult::InvalidState, "Unexpected readback size.");
			}
			std::memcpy(&Value, Bytes->data(), sizeof(Value));
			if (Value != 123)
			{
				return FArdaRHIStatus::Error(EArdaRHIResult::InvalidState, "Unexpected compute-graph output.");
			}
		}
		return {};
	}

The example writes and verifies 123 three times. Its synchronous readback deliberately waits for the requested CPU result; ordinary graph replay can use asynchronous execution and completion handling described in execution. The graph owns its transient physical resources through retirement.

Changing inputs and targets

Frozen parameters, shapes and resource identities change inside an edit. For per-frame data, use a synchronized upload node or imported storage and preserve the graph's entry-state contract. A graph per swap-chain image is useful when each graph retains a stable imported target; retain each graph until its accepted work retires. Node-owned intermediate buffers and textures are obtained using FindOutput.

Terrain composes UploadSettings → Generate → Erode → Triangulate → Draw, with a separate camera upload and overlay. PixelSort composes UploadFrame → Noise → CUDA Sort → Present. Cornell keeps BLAS/TLAS assets externally and rebuilds its TLAS through a node every execution. None of their shader-recording hooks create binding sets or ray tables.

Summary and checkpoints

Operation authors declare semantics; renderer authors compose operations; ArdaInductor supplies physical execution state. Can you identify which output causes each edge? Which inputs persist across frames? Which change requires recompilation? Follow failure cases before authoring a new class.
