ArdaInductor pipeline inference

Compose a pipeline from typed stages

Compose graphics and ray shader stages through typed values, validate complete pipelines, and understand native pipeline creation and reuse.

Persistent dependency-graph nodes describe shader contributions and request pipeline slots. CompileAndWait() infers each live request into a pipeline pattern. The first SubmitAndWait() creates or reuses native PSOs and framebuffers before any commands are recorded. All persistent revisions share the graph's native PSO cache, while each revision owns its compiled plan and prepared runtime. Switching to a newly compiled revision can reuse matching PSOs; selecting a cached revision reuses that revision's runtime as well. Recording callbacks receive the resolved PSO through FArdaDependencyExecutionContext; state helpers apply runtime-prepared bindings and shader parameters, while callbacks supply draw/dispatch arguments. Pipeline descriptions belong to Inductor/Rules/ArdaInductorPipeline.h. The separate Inductor/Compiler/ArdaInductorPipelineCompiler.h exposes inference and native cache-resolution calls. ArdaDependencyGraph.h includes both through the module entry point.

Describe contributions and slots

A registered class uses TArdaNodeDefinition<Node, Parameters, EArdaNodeType::...> and a macro-defined node parameter schema. Its optional static Describe hook returns pipeline contributions and other requirements in FArdaDependencyNodeDesc. Add any number of FArdaInductorPipelineContribution values to mPipelineStages and requests to mPipelines. Each contribution retains a shader; IArdaRHIShader::GetStage() supplies its stage and GetPersistentCacheHash() supplies its content identity. Each request selects mKind, optional mGroup, and a consumer-local mSlot. An empty slot becomes "default"; duplicate slot names on one node fail compilation. The graph assigns mTerminalNodeId, so ordinary node descriptions leave it unset.

For example, this node maps its output to a registered compute shader's parameter schema and contributes the shader retained by its immutable prepared state:

ARDA_BEGIN_NODE_PARAMETER_STRUCT(FArdaComputeParameters)
    ARDA_NODE_SHADER_BUFFER(mOutput, FArdaComputeShader::FArdaParameters, mOutput)
    ARDA_NODE_PARAMETER(uint32_t, mGroupCount)
ARDA_END_NODE_PARAMETER_STRUCT()

FArdaDependencyNodeDesc FArdaComputeNode::Describe(const FArdaParameters&, const FArdaState& State)
{
    FArdaDependencyNodeDesc Desc;
    Desc.mPipelineStages = {State.mStage};
    FArdaInductorPipelineRequest Request;
    Request.mKind = EArdaPipelineStateKind::Compute;
    Request.mSlot = "default";
    Desc.mPipelines.push_back(eastl::move(Request));
    return Desc;
}

The node class also supplies GetMetadata and its execution hook. Its parameter metadata generates a canonical key covering the output identity and group count. An application value without a supported encoder requires an explicit semantic GetCanonicalKey or a TArdaNodeParameterKey specialization. Returning a PSO request alone does not declare resource accesses. Shader and CUDA resource macros inherit their source schema's requirements; attachment and non-shader resource macros declare copies, render targets and native build accesses. Dynamic ranges and bindless entries can be described in the custom hook. See class-authored recipes.

Graphics stage values

Standalone graphics nodes use TArdaNodeDefinition<Node, Parameters, Type> with EArdaNodeType::Vertex, Raster or Pixel. Their named calls return FArdaGraphVertices, FArdaGraphFragments and FArdaGraphPixels respectively. These graph-owned values describe shader dataflow; they are not memory allocations.

const auto Vertices = TriangleVS(Edit, VertexBuffer, IndexBuffer);
const auto Fragments = TriangleRasterize(Edit, Vertices, Width, Height);
TrianglePS(Edit, Fragments, ColorTarget);

Declare the logical input with ARDA_NODE_STAGE_INPUT(Type, Member) in the node parameter schema. The member name is arbitrary. The graph records its producer edge from that metadata automatically. Edit.Order is not used to select or connect these stages. A preprocessing rule validates the chain before ordinary resource dependency resolution and creates a graphics terminal for each pixel operation. Rasterization accepts vertex results, pixel shading accepts fragments, and incompatible, missing, stale or foreign graph values are rejected. The compiler also validates erased stage declarations, so bypassing C++ type checking does not permit rasterizing the output of another raster operation.

Before culling, preprocessing checks every declared graphics stage for a path to a pixel terminal. A standalone vertex operation, an unfinished raster branch or any other orphan stage fails compilation even when its output is unused. A successful explicit FetchBuffer materialization also completes its producer and that producer's upstream stage chain. This is the supported way to capture intermediate results without adding a pixel terminal; failed or unavailable materializers do not satisfy completeness. Stage order, input kinds and ownership remain validated for captured chains. Complete unused draws can subsequently be culled through the ordinary physical-output liveness rules.

Each stage declares its own accesses, shader arguments and bindings. Compilation collects them onto the assembled draw. A vertex node contributes its vertex shader and optional mGraphicsInputLayout; a raster node contributes fixed state through mPipelineStages with a configuration and no shader; a pixel node contributes its pixel shader and framebuffer targets. Stage nodes do not request a pipeline slot or issue a draw themselves. Their optional ConfigureGraphics hooks fill shared FArdaGraphicsWork state and draw arguments, then the executor submits one draw.

If one vertex value feeds two raster operations, there are two assembled draws. The vertex stage executes in both pipelines. Shader objects and compatible PSOs can still be cached and shared; the graph does not silently cache vertex results in a buffer. The compiled raster recipe exercises this fan-out using two render targets.

Pipeline requests, selected stages, and ambiguity

Ray pipelines use the same definition template with RayMiss, RayClosestHit, RayAnyHit, RayIntersection and RayCallable providers returning FArdaGraphRayShader. A RayGeneration terminal selects those values in its provider list declared with ARDA_NODE_STAGE_INPUTS(FArdaGraphRayShader, Member). Preprocessing validates the providers and collects their contributions, resource accesses and bindings onto that terminal. It supplies the default ray-tracing pipeline request when omitted. The terminal retains its authored Record callback for SetRayTracingState and DispatchRays. Provider values can be shared by multiple terminals; unrelated resource ancestry does not add ray shaders to these assembled pipelines. See ray stage registration.

For complete-operation compute, graphics, mesh, ray and work-graph requests, the graph infers each pipeline from the requesting node's own contributions and fixed configuration. Typed graphics and ray preprocessing first merges the stages selected by logical stage values onto their terminal. Resource dependencies and Edit.Order constraints schedule work; they never import another node's shaders, layouts or fixed settings. A missing local stage is an error even if an earlier node uses a suitable shader.

Describe contributes prepared shaders and settings but cannot set stage identity or connectivity. The framework rejects nondefault mGraphicsStage, mRayStage, mGraphicsInput, mRayInputs or mbPipelineStageOnly; EArdaNodeType and the parameter schema are their source of truth.

The lower-level InferArdaInductorPipeline() utility also accepts dependency projections for compiler algorithms and tests. Ordinary graph compilation passes node-local contributions after typed assembly, so that utility does not introduce an alternate graph authoring path.

Use the unified node definition template and typed stage parameter declarations for graphics dataflow. Every declared stage must reach a valid terminal or a successful explicit materializer; unused unfinished stages are rejected.

The grouping rules are explicit:

  • An empty contribution mGroup is shared by every selected group.
  • An empty request mGroup accepts at most one named group within that node's selected contributions.
  • Multiple selected named groups require the request to select one.
  • Distinct shaders for the same stage/export in the selected group are ambiguous; repeating the same stage/content is accepted.
  • Local contributions belonging to other pipeline families are ignored by that request; pixel shaders apply to both traditional graphics and mesh pipelines.
  • Global layouts merge in canonical register-space and semantic order. Equal layouts are deduplicated. Distinct layouts in one space are accepted when their stage visibility is disjoint, matching the RHI graphics binding model; differing layouts with overlapping visibility are rejected. Use compatible shared settings when stages overlap.

For example, one complete graphics operation contributing VS_A in group "terrain" and VS_B in group "water" can share an ungrouped pixel shader. A request with no group fails; Request.mGroup = "terrain" selects VS_A plus that shared pixel shader. Giving both vertex contributions an empty group still fails because they conflict within the selected pipeline. A node may instead request two slots, "terrain" and "water", each with its corresponding group.

The five pipeline families

The resolver maps all five EArdaPipelineStateKind values to the existing RHI pipeline cache:

  • Compute: exactly one compute shader; result member mCompute.
  • Graphics: vertex shader with optional pixel/geometry stages. Tessellation requires paired hull/domain shaders, PatchList topology, and valid patch-control-point settings; result mGraphics.
  • Meshlet: mesh shader with optional amplification and pixel shaders; result mMeshlet.
  • RayTracing: named ray-generation, miss, and callable exports plus named hit groups; at least one ray-generation shader is required; result mRayTracing.
  • WorkGraph: work-graph shaders plus program name, entry point, and nonzero maximum input records; result mWorkGraph.

These are inference capabilities. Native creation still checks the selected device/backend's support and returns its ordinary failure status when a feature is unavailable. The resolver does not translate shader languages or provide a software substitute for unsupported native pipeline features.

Ray-generation, miss, and callable contributions set mExportName. Closest-hit, any-hit, and intersection contributions set a common mHitGroupName to assemble one group; an intersection shader makes it procedural. Use mLocalBindingLayout for a ray export or hit group, and mBindingLayouts for global layouts. Conflicting local layouts or shader exports fail; general export names and hit-group names must be distinct. Null shaders without a settings contribution and empty configured hit groups are rejected.

Work-graph program settings can be provided by the consumer:

auto Settings = eastl::make_shared<FArdaInductorPipelineConfiguration>();
Settings->mKind = EArdaPipelineStateKind::WorkGraph;
Settings->mWorkGraph.mDesc.mProgramName = "MyProgram";
Settings->mWorkGraph.mDesc.mEntryPoint = "MyEntry";
Settings->mWorkGraph.mDesc.mMaxInputRecords = 32;
Request.mKind = EArdaPipelineStateKind::WorkGraph;
Request.mConfiguration = Settings;

Fixed settings and ownership

FArdaInductorPipelineConfiguration holds the five existing pipeline initializers; only the member selected by mKind participates. Attach it to a contribution or request through mConfiguration to supply raster/input-layout settings, ray limits, or work-graph program settings. It may also seed shader fields and global layouts. Later contributions merge with those fields and cannot silently replace conflicting shaders. When several selected contributions supply fixed/program settings, those settings must agree; inference does not choose one by declaration order.

Finish building a configuration before attaching the node. The graph snapshots description configuration values when attaching, while retaining immutable RHI shader/layout objects. Descriptor vectors and strings are owned by that snapshot; changing a caller's configuration alias must not rewrite already-attached node semantics. The same rule is the author's responsibility for arbitrary nested pointers in custom typed parameters: copying a shared_ptr<const T> does not freeze another mutable alias to T. Recording callbacks must use the described, immutable behavior. Replace changed semantics inside a graph edit and give them an updated canonical key. Readback destinations or diagnostic sinks can remain mutable outputs; they must not silently change the declared pipeline or resource behavior.

Framebuffers, keys, and cache lifetime

Graphics and mesh consumers declare mColorTargets and/or mDepthTarget plus matching texture accesses. The runtime materializes their framebuffer and passes it to the cache during pipeline resolution. Empty mColorFormats and an Unknown depth format are completed from its attachments. Set mSampleCount = 0 to derive samples; its default value of one remains an explicit requirement. Explicit formats or sample counts that disagree with the framebuffer fail. Without a framebuffer, the current cache requires nonempty explicit color formats and a nonzero sample count.

FArdaInductorPipelinePattern::mStableKey identifies normalized shader and pipeline semantics before framebuffer completion. It includes pipeline family, shader stages/content hashes, global/local layouts, input layout, fixed state, formats/samples, and ray/work-graph settings. It excludes node IDs, graph instance labels, slot/group names, debug names, and caller-supplied persistent-cache labels. Layout spaces, ray exports/hit groups, and work-graph shaders are canonically ordered, so equivalent contribution orders produce the same key. The resolved result's key also includes the completed framebuffer formats and samples. These semantic keys are separate from native object addresses and the existing cache's internal descriptor keys.

ResolveArdaInductorPipeline() verifies the pattern key, then calls the appropriate FArdaPipelineStateCache::GetOrCreate* method. The in-memory cache compares complete RHI pipeline descriptors, including shader, binding-layout and input-layout object references; it does not look up PSOs by the ArdaInductor stable key. Two separately created shaders or layouts with equivalent contents can therefore produce the same stable pattern key while occupying different in-memory PSO cache entries. Repeated requests that share the same RHI references and matching settings reuse the cached PSO while its entry remains resident. Native persistent caches receive a separate content-derived key during PSO creation; that metadata does not merge the in-memory entries. The graph retains its device-bound cache and compiled typed pipeline references across frames. Repeated ExecuteAndWait() records fresh commands using those resolved references; it does not infer or create the PSO again. Use Graph.GetPipelineCacheStats() to inspect entries, misses, hits, and creation failures for this cache. The lower-level device descriptor-cache counters measure a different layer.

Use the resolved pipeline when recording

During node recording, call Context.GetPipeline("default") or another declared slot name. Class hooks receive public parameters, immutable device state and private instance state separately. The base owns their retained storage. The returned FArdaInductorResolvedPipeline has the corresponding typed reference, such as mCompute or mGraphics; an unknown slot returns null. Use the context state helpers for compute, graphics, meshlet and ray tracing. They supply the inferred PSO, prepared bindings, framebuffer and shader parameters. Work-graph dispatch has a matching helper; automatic binding preparation describes table and local-record handling. For graphics/mesh state, use Context.GetFramebuffer() for the compiled attachments. Then issue the normal draw, dispatch, ray, or work-graph command through GetCommands(). For compute specifically, check SetComputeState()'s status, call the void Dispatch() method, then return FArdaRHIStatus{}.

See ArdaInductorGpuTests.cpp for a complete typed compute node, bindings, consumer-before-producer attachment, and three-frame numerical readback. ArdaInductorPipelineTests.cpp covers the lower-level inference utility's dependency projections, groups, layout conflicts, tessellation pairs, ray exports, work-graph identity, and invalid configurations without a GPU. Graph execution tests separately verify that resource/order edges do not transfer shader contributions. The implementation is in ArdaInductorPipeline.cpp; ArdaInductorRuntime.cpp connects inference to compilation and execution.

Native API references

The native model behind these settings is described by Microsoft's D3D12 pipeline-state overview and Khronos's VkGraphicsPipelineCreateInfo specification. Ray exports, hit groups, and local-root associations follow the concepts in the DirectX Raytracing specification. Microsoft's work-graph mesh-node description explains the native program/state-object model; the currently exposed Arda work-graph fields remain the implementation contract above.

Check stage and dependency edges

Typed stage values select shader composition. Resource and ordering edges control scheduling; they do not supply shaders to another operation.
