Dependency graph documentation

Find the guide that fits your task

Find the appropriate module guide and keep authored pages, compiled examples and the canonical API inventory synchronized.

For application authoring, start with the resource-variable programming model. FArdaGraphEdit records operations such as AllocateTexture, BindTexture, Clear and CopyTo; every reusable node also publishes a named global callable such as CopyBuffer(Edit, Source, Destination). Edit.Commit() checks authoring errors and queues the edit, Graph.CompileAndWait() selects or compiles a persistent revision, and Graph.ExecuteAndWait() runs it. The compiled node recipes demonstrate named callables, automatic registration, output retention and readback.

For imported models, use the offline compilation walkthrough and runtime definition and package API. The status table separates working static CUDA support from remaining compiler, architecture-selection and archive-scaling work.

To add a class-authored operation, follow registering a graph node: declare its class and ARDA_DECLARE_GRAPH_NODE(NodeClass, InvocationName) in the header, define ARDA_DEFINE_GRAPH_NODE(NodeClass, InvocationName) once in its implementation, and implement metadata, canonical keys, resource declarations and recording. The guide distinguishes global C++ callable names, runtime registry identities and per-operation diagnostic names, and covers discovery, linking and failure handling.

Resource descriptors default to AutoDeduction: compilation combines node requirements into concrete SRV, UAV, attachment and buffer usage flags. Explicit usages constrain the allocation; imported resources must already satisfy their consumers. See automatic resource usage for hints, validation and custom rules.

Each frame can record its desired operations afresh on the same graph. Ordered edit hashes form a construction hash; matching constructions reuse the cached graph and compilation results. Successful compilation clears the edit queue and locks edits until ExecuteAndWait() or SubmitAndWait() is attempted. The next ordinary edit starts empty, so omitted operations need no explicit removal. The graph retains up to four revisions by default and can reuse A after an A/B/A sequence. Use CompileAndWait(true) to force compilation, InvalidatePersistentCache() to invalidate reuse, and GetRevisionStats() to inspect cache activity. See revision lifetime and identity for imported resources, retained pointees and error recovery.

The same CopyTo(Edit, Source, Destination) name selects the registered operation from its typed arguments:

Source and destination Registered node
Buffer to buffer FArdaMemoryCopyBufferNode
Texture to texture FArdaMemoryCopyTextureNode
Buffer to texture FArdaGraphBufferToTextureNode
Texture to buffer FArdaGraphTextureToBufferNode
Acceleration structure to acceleration structure FArdaMemoryCopyAccelerationStructureNode

Mixed buffer/texture copies accept a texture slice and buffer layout. An omitted layout or zero row pitch infers a portable aligned pitch for the selected region, preserving the byte offset; the buffer must have room for that pitched footprint. Upload and Readback handle ordinary packed CPU byte vectors.

Start with the persistent dependency graph and ArdaInductor guide for edits, registered typed nodes, scheduling, CUDA sequences and memory planning. The pipeline guide explains stage contributions, named slots, ambiguity, native PSO creation and reuse.

For separate graphics operations, use the vertex, raster and pixel stage templates. Typed intermediate values connect the stages automatically, and a shared vertex value can feed multiple raster branches. Explicit buffer materializers let a node library expose captured results when needed.

The architecture chapter separates graph resources, node definitions and default nodes from inductor configuration, rules, compiler orchestration and runtime. The compilation and scheduling chapter explains ordered, configurable preprocess and compile rule instances derived from FArdaGraphRule, their graph/result transformation contracts, built-in alternatives, a custom ordering policy, memory/cost models and search algorithms. CompileAndWait() publishes or reuses a logical schedule and pending memory plan. The first SubmitAndWait() materializes native resources, pipelines and per-frame execution state; later frames reuse them.

The overview, getting started example, renderer guide and execution guide all use FArdaDependencyGraph. GPU telemetry and adaptive scheduling covers optional per-node timing, EMA/history, nonblocking collection and schedule adoption after frame retirement. Both timing and automatic tuning are disabled by default. Timing observes any selected order; automatic and manual schedule optimization require every selected rule to opt in, preserving stable/custom policies by default. The API reference inventories the current public graph headers. ArdaDependencyGraph.h is an umbrella for the persistent APIs.

Regenerate and validate the inventory using the commands in the backend documentation maintenance guide.
