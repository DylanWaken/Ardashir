Commands and submission

A command list is a CPU-authored program for a GPU queue. Correct production submission requires more than valid calls: it requires resource visibility, queue ordering, lifetime, and bounded CPU/GPU overlap.

Learning objectives

After this chapter, you should be able to:

  • Separate CPU recording, queue submission, GPU start, GPU completion, and CPU retirement as distinct events.
  • Choose graphics, compute, and copy queues and establish same-queue or cross-queue order correctly.
  • Operate the Arda command-list state machine and preserve one device/queue domain.
  • Assemble complete graphics, compute, mesh, or ray-tracing binding state before execution commands.
  • Classify RAW, WAR, and WAW hazards and select transitions, memory/UAV ordering, or queue waits.
  • Decide when automatic tracking, explicit tracking, immediate execution, deferred recording, or ArdaRenderGraph is appropriate.
  • Design a production frame submission pipeline with parallel CPU recording and bounded in-flight resources.

Prerequisites

Read RHI resources and memory and Pipeline states. You should understand resource usage versus current state, subresource ranges, views, binding sets, framebuffers, intrusive ownership, and device affinity.

Commands do not execute when called

Unless immediate execution is explicitly selected, methods on IArdaRHICommandList encode work. They do not imply that the GPU has observed, started, or completed that work.

Fundamentals: CPU recording versus GPU execution

Rendering spans two asynchronous timelines. CPU threads build descriptors, resolve pipelines, and record commands into backend command memory. Submission places closed lists into a queue. The GPU later consumes that queue. Completion is observed through returned submission instances, queue waits, event queries, GPU fences, or device idle.

Five events that must not be conflated

  1. Recorded: a CPU call was encoded into an open command list.
  2. Closed: recording was finalized and can be submitted.
  3. Submitted: ExecuteCommandList or ExecuteCommandLists accepted the work and returned a nonzero instance.
  4. Executing: the queue scheduler has begun GPU processing; this is usually not directly observed by the application.
  5. Completed: a completion primitive proves the GPU no longer needs the associated transient CPU/GPU objects.

Design rationale: deferred recording enables driver batching, command reuse, and multi-threaded CPU construction. Its cost is temporal distance: invalid synchronization or lifetime may fail long after the recording call that caused it.

Queue types, capabilities, and ordering

EArdaRHIQueueType exposes three logical queue classes. Query IsQueueSupported before creating a list.

Graphics
Supports raster work and normally compute/copy operations. It is the required portable baseline and the safe fallback when dedicated queues are absent.
Compute
Supports dispatch-oriented work without rasterization. A distinct asynchronous compute queue can overlap graphics only when dependencies, bandwidth, and hardware scheduling allow it.
Copy
Specializes transfers. It can isolate uploads/readbacks from graphics, but queue ownership and waits may outweigh benefit for small transfers.

Same-queue order

Commands within one list retain encoded order. Lists submitted to the same queue execute in submission order. That establishes execution order, but resources still need correct states and memory visibility. A barrier is not a substitute for queue submission; queue order is not a substitute for a required barrier.

Cross-queue order

Different queues can progress independently. If compute consumes a buffer produced on graphics, call QueueWait(waitQueue, executionQueue, instance) so the waiting queue does not pass the producer instance. The returned instance belongs to the execution queue that produced it.

Parallel queues do not guarantee faster frames

Queues may share execution units, caches, and memory bandwidth. Overlap only independent work with enough duration to amortize synchronization. Measure GPU timelines rather than inferring concurrency from queue names.

The command-list state machine

CreateCommandList fixes the owning device, queue type, and immediate-execution mode. GetDevice() and GetQueueType() make that affinity inspectable.

  1. Created: the list exists for one queue and device.
  2. Recording: Open() begins encoding.
  3. Closed: Close() finalizes encoded work.
  4. Submitted: device execution returns a queue instance ID. Submission does not mutate the list into a completion primitive.
  5. Reusable: Reset() reopens a closed list and discards its prior recording. Reuse only after any native allocator and referenced-work constraints are satisfied by the implementation contract.

Lifecycle calls return FArdaRHIStatus because open/close/reset ordering and backend finalization can fail. Record only while open; submit only after close; never treat a successful close as GPU completion.

Submission instance IDs

TArdaRHIResult<uint64_t> from execution contains a nonzero instance on success. It names a point in one queue’s submission stream. Store it with the queue identity. Passing zero to QueueWait is invalid; comparing instance values from unrelated queues has no ordering meaning.

Graphics, compute, mesh, and ray-tracing state

Execution commands consume state previously bound into the command list. Arda packages related state into retained value objects rather than exposing every native state mutation independently.

Graphics state

FArdaRHIGraphicsState carries the graphics pipeline, framebuffer, binding sets, vertex buffers, optional index buffer and format, viewports, and scissors. SetGraphicsState must succeed before draw calls that depend on it.

  • Pipeline color/depth formats and sample count must match the framebuffer.
  • Binding sets must match pipeline binding layouts and shader visibility.
  • Vertex buffers must satisfy the input layout.
  • Index buffer format, offset, and range must cover indexed draw arguments.
  • Viewports and scissors must describe intended framebuffer regions.

Compute and specialized state

FArdaRHIComputeState binds a compute pipeline and binding sets before Dispatch. FArdaRHIMeshletState adds framebuffer and raster regions for DispatchMesh. FArdaRHIRayTracingState binds a shader table and global sets before DispatchRays. The latter two are capability-gated.

Use FArdaPipelineStateCache::SetGraphicsPipelineState and SetComputePipelineState when renderer code starts from high-level pipeline initializers. These resolve the PSO and place it into command state before binding.

Command families

Draw and indexed draw
Draw consumes vertex/instance counts; DrawIndexed consumes index data and base-vertex semantics through FArdaRHIDrawArguments.
Dispatch
Dispatch launches compute thread groups. Group counts are not thread counts; the shader declares threads per group. Mesh and ray dispatches require their capabilities and state.
Copy and upload
WriteBuffer, CopyBuffer, CopyTextureFromStaging, and CopyTextureToStaging move data. Bounds, alignment, states, pitches, and queue support remain caller-visible contracts.
Clear
ClearTexture, ClearTextureUInt, ClearDepthStencilTexture, and ClearBufferUInt initialize compatible resources. A clear is an ordered write and participates in hazards.
Ray-tracing builds
BuildBottomLevelAccelStruct, BuildTopLevelAccelStruct, and BuildTopLevelAccelStructFromBuffer consume build inputs and write acceleration storage. Build flags affect update, compaction, speed, and memory tradeoffs.
Opacity and sampler feedback
BuildOpacityMicromap, ClearSamplerFeedbackTexture, and DecodeSamplerFeedbackTexture encode specialized workflows and must be capability-gated.
Markers and timer queries
BeginMarker/EndMarker create nested diagnostic regions. BeginTimerQuery/EndTimerQuery record GPU timestamps; poll and read only after availability.

Resource hazards, states, and barriers

A hazard exists when accesses can overlap without the required execution order and memory visibility. Classify the earlier and later accesses:

RAW — read after write
A later read must observe an earlier write. Examples: sample a render target, consume compute output, or draw from an uploaded vertex buffer.
WAR — write after read
A later write must not overwrite storage while an earlier read still consumes it. This matters across queues and when aliasing/reusing transient memory.
WAW — write after write
Two writes require deterministic order when the latter depends on replacing or accumulating after the former.

Resource states

EArdaRHIResourceState communicates intended access and layout: copy source/destination, render target, depth read/write, shader resource, unordered access, present, acceleration-structure roles, and more. A transition barrier reconciles previous and next state and establishes native synchronization as required.

const rhi::FArdaRHITextureSubresourceRange mipZero{0, 1, 0, 1};

if (auto status = command->SetTextureState(
        *sceneColor,
        mipZero,
        rhi::EArdaRHIResourceState::RenderTarget); !status)
    return status;

command->CommitBarriers();
command->ClearTexture(*sceneColor, mipZero, {0.f, 0.f, 0.f, 1.f});

// After rendering, make mip zero visible to shader reads.
command->SetTextureState(
    *sceneColor,
    mipZero,
    rhi::EArdaRHIResourceState::ShaderResource);
command->CommitBarriers();

Automatic versus explicit tracking

With automatic barriers enabled, SetTextureState, SetBufferState, and SetAccelStructState update tracked intent; CommitBarriers emits pending work. BeginTrackingTextureState and BeginTrackingBufferState seed externally known state.

SetAutomaticBarriers(false) transfers correctness to the caller. Use it only when a higher-level scheduler has complete access information and can prove boundary states. Mixing external transitions with stale internal tracking is worse than choosing one coherent authority.

UAV ordering

Consecutive UAV uses can remain in UnorderedAccess state yet still have RAW or WAW dependencies. A state transition may therefore be unnecessary while a UAV memory-ordering barrier is still required. SetUAVBarriersForTexture and the buffer equivalent control per-resource automatic UAV barriers for advanced batching.

Optimization requires a proof

Disable a UAV barrier only when accesses are disjoint or ordering is otherwise guaranteed. “Same state” and “same queue” do not prove that writes are visible to later shader invocations.

Cross-queue waits, fences, and queries

Queue-to-queue dependencies

Use submission instance IDs and QueueWait for GPU-side cross-queue order. The CPU can continue recording while the waiting queue stalls at the dependency. Place the wait before submitting dependent work according to the backend contract and keep producer/consumer queue identities explicit.

Event queries

SignalEventQuery inserts completion on a queue. PollEventQuery supports non-blocking retirement; WaitEventQuery blocks the CPU; ResetEventQuery prepares reuse after completion.

GPU fences

Fences expose the same signal/poll/wait/reset pattern through SignalGpuFence, PollGpuFence, WaitGpuFence, and ResetGpuFence. Arda’s facade tracks one signal at a time, so use a ring of fences for multiple frames in flight.

Timer queries

Begin and end a timer query while recording. After GPU completion, poll availability, read GetTimerQuerySeconds, then reset. Timer queries measure GPU intervals, not CPU recording or queue wait time unless the measured region includes those effects.

WaitForIdle is appropriate for teardown, tests, initialization transitions, and rare recovery. Calling it every frame serializes CPU and GPU and destroys queue overlap.

Immediate versus deferred command lists

The second CreateCommandList argument, bImmediateExecution, configures backend immediate execution. The default false creates a conventional deferred list that records a batch for explicit submission.

Deferred
Preferred for production frames. It amortizes submission, supports parallel CPU recording, preserves clear list boundaries, and allows queue scheduling.
Immediate
Useful for narrow bring-up, tools, tiny synchronous setup paths, and diagnosis where simplified latency matters more than batching. It does not erase resource-state, ownership, or completion requirements.

Tradeoff: immediate execution can make a simple experiment easier to reason about but can hide accidental serialization and produce a frame architecture that scales poorly. Keep the production path deferred and measure any exception.

ArdaRenderGraph integration

ArdaRenderGraph raises command scheduling from imperative transitions to declared pass accesses. FARDGBuilder compiles live passes, resource lifetimes, queue assignments, raster groups, and FARDGQueueDependency values before recording.

  • Logical textures, buffers, views, and acceleration structures are materialized at execution.
  • Declared access lets compilation derive boundary barriers and cross-queue waits.
  • Transient lifetimes permit pool reuse and safe heap aliasing when supported.
  • FARDGExecuteOptions::mbParallelRecording records independent pass waves concurrently.
  • FARDGExecutionResult reports submitted-list count, queue waits, pool reuse, immediate mode, virtual heaps, aliasing, and last submitted instances.

Pass callbacks that use FARDGPassExecutionContext can validate declared physical-resource access. A raw IArdaRHICommandList& callback can use independently retained resources, so the graph cannot prove declaration completeness. Reserve the unsafe raw path for operations the typed context cannot express.

Design rationale: direct RHI recording maximizes local control but distributes hazard reasoning across call sites. A render graph centralizes whole-frame dependency knowledge and parallel scheduling, at the cost of declaration discipline and compilation machinery.

Worked example: copy, compute, then graphics

using namespace arda;

auto copyResult = device->CreateCommandList(rhi::EArdaRHIQueueType::Copy);
auto computeResult = device->CreateCommandList(rhi::EArdaRHIQueueType::Compute);
auto graphicsResult = device->CreateCommandList(rhi::EArdaRHIQueueType::Graphics);
if (!copyResult || !computeResult || !graphicsResult)
    return rhi::FArdaRHIStatus::Error(
        rhi::EArdaRHIResult::Unsupported,
        "Required queue is unavailable.");

auto copy = eastl::move(copyResult.mValue);
copy->Open();
copy->SetBufferState(*workBuffer, rhi::EArdaRHIResourceState::CopyDest);
copy->CommitBarriers();
copy->WriteBuffer(*workBuffer, uploadData, uploadBytes);
copy->Close();
auto copied = device->ExecuteCommandList(copy);
if (!copied)
    return copied.mStatus;

device->QueueWait(
    rhi::EArdaRHIQueueType::Compute,
    rhi::EArdaRHIQueueType::Copy,
    copied.mValue);

auto compute = eastl::move(computeResult.mValue);
compute->Open();
compute->SetBufferState(
    *workBuffer, rhi::EArdaRHIResourceState::UnorderedAccess);
compute->CommitBarriers();
compute->SetComputeState(computeState);
compute->Dispatch(groupCount, 1, 1);
compute->Close();
auto computed = device->ExecuteCommandList(compute);
if (!computed)
    return computed.mStatus;

device->QueueWait(
    rhi::EArdaRHIQueueType::Graphics,
    rhi::EArdaRHIQueueType::Compute,
    computed.mValue);

auto graphics = eastl::move(graphicsResult.mValue);
graphics->Open();
graphics->SetBufferState(
    *workBuffer, rhi::EArdaRHIResourceState::VertexBuffer);
graphics->CommitBarriers();
graphics->SetGraphicsState(graphicsState);
graphics->Draw(drawArguments);
graphics->Close();
auto drawn = device->ExecuteCommandList(graphics);
if (!drawn)
    return drawn.mStatus;

This illustrates the dependency chain, not a universal recommendation. If dedicated queues are absent, record all three phases on graphics. In production, propagate every returned status, retain all state/resources through completion, and signal a frame fence after the final submission.

Command and submission invariants

  1. A command list records only while open and submits only after successful close.
  2. The list, every bound object, and every accessed resource belong to one device.
  3. Every operation is supported by the list’s queue and the device capabilities.
  4. Pipeline, binding sets, framebuffer, vertex/index data, and dynamic state are mutually compatible.
  5. Every RAW, WAR, and WAW dependency has sufficient execution order and memory visibility.
  6. Tracked state begins from the actual state and ends in the state promised to the next owner.
  7. Submission instances are nonzero, paired with their producer queue, and used only for valid waits.
  8. All CPU and GPU objects referenced by submitted work survive until completion is proven.
  9. Frame-resource reuse is bounded by fences or queries, never by elapsed CPU time.

Failure analysis

InvalidState while recording
Check open/close/reset phase, required bound state, timer-query pairing, marker nesting, and whether an operation is legal after finalization. Repair the lifecycle; blind retry preserves the defect.
WrongDevice
Trace command-list and resource creation. Pipeline-cache objects, framebuffers, views, queries, and imported resources must all belong to the same device domain.
Unsupported
Check queue availability and exact feature flags for mesh dispatch, ray tracing, sampler feedback, opacity micromaps, queries, or other specialized commands. Select a graphics-queue or feature fallback.
GPU data is stale or intermittently corrupt
Classify the accesses, then inspect subresource range, initial state, transition point, UAV ordering, cross-queue wait, and CPU flush/upload lifetime. A CPU-success status does not validate GPU memory dependency.
GPU hang or device removal
Enable native validation, preserve marker breadcrumbs, capture the first failing frame, and inspect out-of-bounds draw/dispatch/copy, invalid descriptors, released resources, and cyclic queue waits.
Frame rate collapses despite low GPU work
Look for per-frame WaitForIdle, tiny submissions, excessive barriers, synchronous query waits, command-list churn, serialized recording, and queue ping-pong.
Parallel recording is nondeterministic
Audit shared CPU allocators, mutable descriptor tables, global caches, pass parameter lifetime, and submission ordering. Recording different lists can be parallel; mutating shared state without a threading contract cannot.

Performance guidance and production frame submission

  1. Retire a frame slot. Poll or wait for that slot’s completion fence before reusing command allocators, upload ranges, transient descriptors, and dynamic buffers.
  2. Acquire presentation state. Obtain the next swap-chain image and its known initial/present state.
  3. Build work. Update immutable pass data, compile ArdaRenderGraph, or construct a direct dependency schedule.
  4. Record in parallel. Assign independent pass waves to worker threads. Give each worker private transient recording storage and avoid mutable shared descriptors.
  5. Submit coarse batches. Preserve dependency order while batching compatible same-queue lists with ExecuteCommandLists.
  6. Insert cross-queue waits. Wait only at the first true consumer, not at arbitrary frame-wide boundaries.
  7. Transition and present. Return the swap-chain image to Present state and submit/present through the presentation contract.
  8. Signal completion. Signal the frame slot’s fence/query after the last submission that touches its resources.
  9. Retire asynchronously. Continue CPU work for later frames; release deferred resources and run garbage collection only when completion proves safety.

Practical optimization rules

  • Batch enough work per list to amortize close/submit costs, but preserve parallel recording and useful queue overlap.
  • Place barriers near the first consumer while coalescing compatible transitions. Avoid transitioning a whole texture when one mip is sufficient.
  • Use async compute only for proven overlap. Queue waits and cache/bandwidth contention can make a nominally parallel schedule slower.
  • Use markers on frame, pass, and major algorithm boundaries. Keep labels stable so captures compare across builds.
  • Measure CPU recording, queue latency, and GPU duration separately. Timer queries alone do not expose CPU bottlenecks.
  • Keep two or three frame contexts only when latency requirements permit; more buffering can improve throughput while increasing latency and memory.
  • Prefer graph-derived barriers for graph-owned resources and explicit direct-RHI barriers for external/manual work. Document the state handoff between authorities.

Summary

Command recording constructs a future GPU program; closing finalizes it; submission orders it on one queue; barriers make resource accesses visible and legal; waits connect otherwise independent queues; fences and queries prove completion. Arda exposes direct control through IArdaRHICommandList and whole-frame scheduling through ArdaRenderGraph. Production performance comes from correct batching, parallel recording, selective queue overlap, and fence-based resource retirement—not from removing synchronization blindly.

  3. When can two UAV operations remain in one state yet still require ordering?
  4. What information must accompany a submission instance ID for it to be meaningful?
  5. Which frame resources must be retired by a fence before reuse?
