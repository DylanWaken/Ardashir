1. Recommendation and scope

Build an engine-neutral material graph compiler, with an Unreal editor exporter as its first asset frontend. Compile a declared subset of Unreal expression semantics into an Ardashir-owned material evaluation interface, then use ArdaBackend's existing compiler services to produce DXIL and SPIR-V. Keep graph assets, compiled programs, material instances, device resources, and renderer pass pipelines as separate objects.

The first useful milestone is an uncooked Unreal material exported through the editor, compiled outside Unreal, and rendered on a static mesh in Ardashir with texture and scalar/vector instance overrides. Start with Surface/Opaque/Unlit and attribute visualization; add Default Lit, masking, functions, and vertex deformation through independently verified milestones. Preserve the ability to author the same neutral graph without Unreal.

“Supports Unreal material graphs” must be a versioned compatibility contract, not a claim that any .uasset or any Unreal shader will work. Distinguish:

  1. Asset extraction: recover expressions, connections, defaults, dependencies, and effective instance settings from an uncooked project.
  2. Expression compatibility: reproduce supported node outputs, casts, parameters, and stage behavior.
  3. Renderer compatibility: supply geometry, coordinates, texture semantics, lighting, passes, and scene services required by those outputs.
  4. Image compatibility: compare controlled outputs with Unreal; graph compatibility alone does not reproduce Unreal lighting, temporal filtering, or tone mapping.

Assumptions for this plan: standalone Ardashir rendering is the target; an editor-side Unreal plugin/commandlet can access source assets; Vulkan and D3D12 are the initial backends; existing Unreal binaries and renderer internals are not an execution dependency of the standalone runtime. Live hosting inside Unreal, cooked-only graph recovery, a graph editor UI, and full Substrate rendering are separate later projects. These assumptions should be revisited if the intended deployment is an in-process replacement renderer.

Related documents: archived scene representation plan, Unreal scene/material integration requirements, and Arda shader infrastructure. Material and scene systems remain proposals outside the current infrastructure, tests and tracing source tree.

3. How Unreal's material system works

3.1 Authoring data is not the editor canvas

UMaterial owns settings such as domain, blend mode, shading models, two-sidedness and usage. Its editor-only data holds root material inputs and an expression collection. UMaterialExpression subclasses hold node semantics and node-specific properties. The relevant connection is FExpressionInput: an expression reference, output index, input name and channel mask. Node positions/comments belong to authoring presentation and should not affect executable identity. U01, U02, U03

Export semantic inputs and properties, not a screenshot or only UMaterialGraph editor nodes. The editor graph can be rebuilt around expression objects. GetExpressions is editor-only data; property input access and expression collection access require editor builds. The exporter must run while uncooked authoring data exists. A cooked material's shaders and runtime parameters are not a portable serialized expression graph. U01

Use FExpressionInputIterator / GetInput and a class-handler registry for this revision. GetInputsView is deprecated. Generic reflection can help inventory properties, but cannot decide which fields affect compilation, what an unconnected pin means, or how specialized inputs/functions are evaluated. U03

3.2 Compile a property from its root, with context

In the default translator, FExpressionInput::Compile calls FMaterialCompiler::CallExpression using a key that includes the expression, output index, material attribute and previous-frame context, then applies the connection mask. Reroutes are traced. UMaterialExpression::Compile implementations translate node behavior into compiler operations; for example Add resolves its disconnected input constants before calling Compiler->Add. U02, U04, U05

FHLSLMaterialTranslator::CallExpression caches expression results in the appropriate function/stage context, detects re-entrant evaluation, and tracks compilation state. A pointer-only visited set is insufficient: the same node can produce different outputs, attributes, stages or previous-frame values. Substrate also has special handling rather than ordinary expression deduplication. U06

Arda should similarly start from active material roots, resolve the selected static variant, track a complete evaluation context and traverse reachable dependencies. Validate graph structure independently, but do not reject an unsupported operation solely because it lies in a provably unused static branch. A malformed reference or cyclic function dependency must still produce a deterministic diagnostic.

3.3 This checkout has two translation paths

The default is still the legacy translator. r.Material.Translator.EnableNew defaults to false. UMaterialInterface::IsUsingNewHLSLGenerator additionally checks the material's bEnableNewHLSLGenerator and restrictive-material mode. FMaterial::Translate dispatches to Translate_Legacy or Translate_New. U07, U08

The legacy route uses FHLSLMaterialTranslator, expression code chunks, type/cast handling, uniform expressions and HLSL template generation. The new route in this revision is MIR, through FMaterialIRModuleBuilder and FMaterialIRToHLSLTranslation. Expression classes expose Build as well as legacy Compile. Older descriptions of an HLSL-tree route should not be treated as the implementation of this checkout. U03, U07, U09

Both routes populate material compilation output and provide /Engine/Generated/Material.ush to shader compilation. The generated material code is consumed within Unreal's material/pass shader framework; it is not a complete standalone shader entry point. U07, U10

Adaptation: use legacy behavior as the initial compatibility oracle, with the exporter recording the actual translator settings. Adopt a small typed IR for Arda, informed by MIR's separation of building, analysis and emission. Do not port both Unreal compilers, and do not silently compare a legacy result with a MIR reference if they differ.

3.4 Functions, attributes and layers have real semantics

A material function call is not just a differently colored subgraph. Unreal links function inputs to the caller, pushes function context, compiles a requested output, and restores the previous context. Function inputs can return to caller context, use configured preview/default values, or report missing required inputs. Parameter ownership and nested call identity matter. U11

Function call-site identity belongs in evaluation caching and diagnostic provenance; it does not automatically create a new namespace for global named parameters. Preserve Unreal's name/association/index identity separately from expansion scope. Repeated ordinary function calls can refer to the same global parameter; layer/blend ownership changes are explicit. U11, U13

Material Attributes are a typed set of properties with individual defaults, frequencies and GUID identities. Make, Set, Get, Break and blend operations must preserve absent attributes and property-specific behavior. Do not collapse them into a generic float vector. The attribute map specifies, for example, Base Color = (0,0,0), Metallic = 0, Specular = 0.5, Roughness = 0.5, Normal = (0,0,1), Emissive = 0, AO = 1, Opacity/Opacity Mask = 1, and WPO = 0; WPO is a vertex property. These are attribute defaults, not permission to overwrite stored root-input constants or other effective material settings. U12

Material Layers resolve an instance-specific layer/blend stack and parameter associations before compiling its resulting functions. Preserve stack order, enabled entries, layer overrides and blend inputs. Two parameters with the same name in different layers are distinct. U11, U13

Implement ordinary functions and Material Attributes before instance-editable Material Layers. Traditional attribute blending and Substrate closure layering are different operations. Substrate must not be flattened to a base-color/roughness tuple without an explicitly labeled approximation. U11, U12; see also Epic's layering overview and Substrate overview.

Project Substrate mode and explicit Substrate graphs are separate facts. This checkout's project generation enables Substrate for new projects, while its C++ cvar default remains off; existing legacy-authored roots can pass through hidden Substrate conversion. Export r.Substrate, r.Substrate.ProjectGBufferFormat, relevant overrides and whether Front Material is explicitly authored. Supported legacy roots can still be translated into Arda's legacy surface ABI from such a project; explicit closure graphs remain unsupported initially. Record the reference renderer's actual configuration when comparing lighting. U19, U26, U27

3.5 Static specialization and runtime instances are separate

Unreal parameter identity includes name, association and index (GlobalParameter, LayerParameter, BlendParameter), not just a string. Resolve the instance parent chain and layer remapping to obtain effective values. Preserve both identity and provenance so overrides remain explainable. U13, U14

If the exporter uses GetParameterValue, choose lookup flags deliberately: CheckInstanceOverrides includes the leaf's override, and CheckNonOverrides allows defaults. A leaf-overrides-parent-overrides-base fixture must verify the result; reading only raw parameter arrays or using the wrong flags loses effective values. U14

Static switches/component masks and relevant base-property overrides affect shader selection. This revision also allows StaticSwitchParameter to opt into DynamicBranch: export that setting and classify the operation by its behavior, not its class name. Such a dynamic Boolean is a runtime uniform; its branches cannot be removed using the initial parameter value. UpdateStaticPermutation compares effective static settings and can recache resource shaders. Scalar/vector/compatible texture parameter updates instead update render-thread values and uniform resources without changing shader code. A texture replacement that changes resource dimensionality or sampler semantics is not automatically a compatible dynamic update. U05, U14, U19

The material shader map identity accounts for more than graph text: material state, static parameters, platform/feature/quality information and shader/vertex-factory dependencies participate in compilation and cache identity. Shader-map reuse and PSO reuse are separate: pipelines also depend on pass state and render-target configuration. U15, U16

Arda should compile only used static combinations, impose a variant budget, and report the factors creating variants. Do not multiply every Boolean switch by every backend, geometry class and pass indiscriminately. Epic's material instance guide also documents the runtime/static distinction and permutation cost.

3.6 Uniform expressions and preshaders are a CPU/GPU partition

Unreal can separate material-uniform work from vertex/pixel evaluation. FUniformExpressionSet carries numeric parameters, defaults, typed texture bindings, uniform evaluation/preshader data and buffer layout. FillUniformBuffer resolves current parameter values and evaluates either the legacy preshader route or the newer stream before filling GPU-visible storage. This is more than a collection of literal constants. U17, U18

Classification for Arda should distinguish compile constants, material-instance uniform values, frame/view values, primitive/instance values, vertex values and pixel values. Time is not a compile constant; a per-view value must not be cached solely by material instance; a per-primitive value must not be shared across draws accidentally.

Start with constant folding and direct uniform parameter loads. Uniform-only arithmetic can initially execute in the shader. Add a small Arda-owned uniform evaluator only when measured useful, with dependency epochs and CPU/GPU equivalence tests. Reusing Unreal preshader bytecode would introduce another versioned interpreter and layout dependency without removing the renderer ABI problem.

3.7 Textures, derivatives, coordinates and casts determine correctness

Node names are insufficient for translation. The following source behavior must drive the semantic tests:

  • Defaults and coercion: Add/Multiply/Lerp have node-specific disconnected defaults. ValidCast and ForceCast distinguish replication, truncation and zero-extension behavior. Explicit conversion operations should exist in Arda IR; do not leave conversion entirely to HLSL implicit casts. U05, U19
  • Math: Unreal Sine scales input by its configured period; Power contains its own constant and domain behavior; If has an equality threshold and optional equality input. Translating these names directly to sin, pow, and a binary conditional can change results. Match the pinned translator's behavior, including edge cases. U05, U19
  • Sampling: texture object and sampled value are distinct types. Preserve sampler type/source, UV channel, addressing, filtering, mip mode, bias, explicit gradients, normal decoding and view-dependent mip behavior. TextureSample checks derivative inputs and stage restrictions; in the legacy route, non-pixel sampling is forced to explicit mip level, defaulting to zero if no level was provided. U20
  • Derivative domain: implicit raster derivatives require a valid pixel context. Vertex, ray and generic compute evaluation need a defined explicit LOD/gradient policy. Unreal's translator carries analytic derivative information; Arda must not claim full parity merely because raster Sample works. U19, U20
  • Coordinates: record UV orientation, world/local/view spaces, current versus previous transforms, world-position mode, tangent basis/handedness and units. Unreal's material template includes large-world and translated-world inputs. Preserve the relevant origin convention; do not reduce large absolute world positions to float3 silently. U10
  • Normals: distinguish tangent-space material normals from geometric/world normals. Match texture import decode, tangent handedness, mirrored transforms and two-sided policy before judging lighting parity. Renderer and texture conversion responsibilities are part of this contract.

3.8 Renderer integration is the other half of a material

FMaterialPixelParameters, FMaterialVertexParameters and FPixelMaterialInputs are the interface between generated expressions and Unreal shader consumers. They draw on vertex factories, scene/view data, primitive inputs and renderer services. Material shaders are compiled for the passes and vertex factories that use them. A shader map does not become executable in Arda by rebinding its textures. U10, U15, U16

Opaque color, masked depth/shadows, velocity, WPO and ray visibility must agree. Scene Depth/Scene Color, virtual textures, landscape weights, particle attributes and Substrate require supporting services or passes. The correct compiler result for an unavailable service is a capability diagnostic, not a plausible-looking constant.

3.9 Shader maps, compilation jobs and render-thread publication

FMaterialResource implements the material compilation/rendering contract for a material and optional instance at a platform/quality setting. FMaterialShaderMap contains the compiled variants and compilation output. FMaterialRenderProxy supplies render-time parameter lookup, uniform-expression caching and material/fallback selection. These are different responsibilities from the UMaterial authoring asset. U28, U29

The shader-map path checks reusable in-memory/cached data, constructs the required material and mesh-material shader jobs, and submits them through GShaderCompilingManager. FMaterialShaderMap::SubmitCompileJobs enumerates relevant shader/vertex-factory combinations; Compile supports deferred work or an explicit synchronous finish. DDC load/save stores derived compiled data, while cooking can serialize platform shader resources for runtime use. It is not necessary to reproduce Unreal's entire shader worker/DDC service to adopt these boundaries. U16, U23

Publication also has a thread boundary: FMaterial::SetGameThreadShaderMap queues an update for rendering, with separate rendering-thread shader-map state. Uniform-expression caches must correspond to the selected map/layout. Arda should adopt the same invariant—code, layout, instance bindings and publication version agree—using its own immutable snapshots and GPU retirement mechanism. U04, U29

5. Proposed architecture

All names in this section are proposed, not existing APIs.

5.1 Module boundaries

  • Source/ArdaMaterial: graph schema, versioning, validation, parameter identity, typed IR, semantics, HLSL generation and diagnostics. CPU-only tests; no Unreal or device requirement. Depend on ordinary project utilities and optionally ArdaGraph where useful.
  • Source/ArdaMaterialRuntime: device-specific program loading, uniform packing, instance resources, pipeline variants and retirement. Depend on ArdaMaterial and ArdaBackend. Keep RDG-specific binding glue in a renderer adapter so graph semantics do not depend on RDG.
  • Tools/Unreal/ArdaMaterialExporter: proposed editor plugin and commandlet, built by Unreal Build Tool against the pinned checkout. CMake must not require Unreal to build Ardashir.
  • Tools/ArdaMaterialCompiler: proposed command-line import/compile/cook tool. Produce diagnostics, generated HLSL, binding manifest and backend artifacts; support inspect-only and strict compatibility modes.
  • Source/ArdaTests/Examples/MaterialPreview: proposed small raster consumer, with a plane and a tangent-bearing mesh, attribute visualization and a deterministic capture mode. Later connect material handles to the planned ArdaScene schema.

Do not create all modules before proving the first slice. Introduce each target when it gains its first executable responsibility. Register CMake subdirectories in dependency order and follow ardashir_add_module / ardashir_add_module_tests conventions. A13

5.2 Export/package contract

Use a readable, versioned interchange manifest first; JSON is a proposed format, not a serialization ABI tied to UObjects. Separate graph/program data from texture payloads. The minimum records are:

ProducerSchema version, exporter version, Unreal version/commit, translator selection, Substrate/GBuffer configuration, relevant project/platform/quality switches and material source path.
Material settingsDomain, blend/shading model, two-sided and tangent-normal mode, mask threshold, active root inputs, base-property overrides, required usage/capabilities.

Extraction should be deterministic and sorted by stable identity. Resolve redirects and dependencies inside Unreal, retain enough source information to re-export, and avoid relying on collection order or pointer addresses. Use class handlers to serialize semantic settings, including hidden node properties such as Sine period, If threshold and Texture Sample mip mode. Export all relevant roots, then let the compiler select the target's active roots.

Texture asset paths alone are insufficient for standalone rendering. The exporter/converter must produce portable payloads or refer to a separate asset package with verified content identity. Pin sRGB handling, normal-map green-channel policy, compression/decompression, alpha and mip generation; distinguish source pixels from Unreal platform-cooked bytes. A live external texture handle is a separate integration mode.

The import validator enforces size/depth limits, valid IDs, known schema versions, supported enum values, no dangling edges and bounded function expansion. Asset strings are data, not shell commands or unconstrained filesystem paths. Unsupported operations retain their class and source location so inventory mode can report them before code generation.

5.3 Typed graph and lowering

Use two deliberately small representations:

  1. Semantic graph: retains imported node behavior, pins, named attributes, function boundaries and diagnostics provenance.
  2. Typed value IR: lowered operations with explicit scalar/vector types, texture/sampler handles, static Boolean versus runtime Boolean distinction, casts, attributes, stage and dependency classification.

The initial IR can be a DAG of immutable values with stable local IDs; a general control-flow compiler is unnecessary for the first arithmetic subset. Add blocks/control flow only for supported operations that require it. Do not model every numeric value as float4 or erase resource types.

Compiler order:

  1. Validate package structure and resolve parent/function/layer dependencies.
  2. Resolve effective static parameters, target settings and active material properties.
  3. Expand reachable function calls with scope-aware identities; specialize static branches.
  4. Type-check and insert the exact permitted casts; apply node and property defaults.
  5. Propagate required geometry/scene inputs and stage restrictions backward from roots. Order cross-property dependencies explicitly: the legacy translator evaluates Normal before properties that can read the resolved pixel normal. Detect feedback through material-normal reads rather than using arbitrary root iteration order. U19
  6. Partition constant, uniform, vertex and pixel evaluation; reserve previous-frame context.
  7. Fold constants, eliminate dead values and deduplicate pure expressions within compatible contexts.
  8. Allocate varyings and material bindings deterministically; enforce target limits.
  9. Emit HLSL plus a source map, resource manifest, uniform layout and feature requirements.
  10. Submit owned backend jobs; validate artifacts and package them atomically.

Memoization keys must include function-call scope, node/output, selected attribute, stage, static environment and previous-frame mode as applicable. CSE must respect context, resource access and derivative validity. Preserve disconnected input behavior and report cycles with a full asset/function/node chain.

5.4 Material evaluation ABI

Define an Arda-owned, versioned ABI shared by generated code and pass templates:

  • FArdaMaterialVertexContext: local/world positions, normal/tangent, UVs, vertex color, primitive/instance data, current/previous transforms and time when requested.
  • FArdaMaterialPixelContext: interpolated geometric data, tangent basis, UVs/gradients, view direction, position/origin data, front-face state and explicitly supported scene inputs.
  • FArdaMaterialSurface: named BaseColor, Metallic, Specular, Roughness, Normal, Emissive, AO and OpacityMask fields for the initial legacy surface model.
  • EvaluateMaterialVertex, EvaluateMaterialSurface, and a coverage entry point or shared coverage function for masked passes. These names describe proposed contracts, not drop-in Unreal function signatures.

Keep lighting/BSDF evaluation outside the expression compiler. Define exactly which representation the Normal output uses and where conversion/normalization happens. Keep vertex world-position offset separate from surface outputs. Reject unsupported shading-model outputs instead of silently mapping every model to Default Lit.

Start with an explicit static-mesh geometry adapter that provides selected UV channels, tangent basis and vertex colors. Missing required streams should cause a capability failure or a documented geometry conversion. Future skeletal/instanced/particle adapters can share the material ABI while supplying different contexts. Geometry adapters take the role needed from Unreal vertex factories without reproducing Unreal's entire registry.

For large-world inputs, initially support local/camera-relative operations with an exported origin and a tested conversion policy. Reject absolute/LWC operations outside the implemented precision envelope. Expose the coordinate convention in the package and tests rather than assuming Arda already matches Unreal's units and basis.

5.5 Generated shaders and the existing backend compiler

Add an owned material compile request/descriptor that can call existing backend configuration and invocation hooks. Preserve the current registered-global-shader workflow and its tests. Initially write generated HLSL to an immutable per-program directory; a future virtual in-memory include interface is optional. A01, A02, A03

The request must own source identity, source/dependency contents or immutable paths, entry point, stage, profile, sorted defines, backend target, compiler settings, layout identity and diagnostic source map. Do not mutate a frozen global source registry for every material or retain pointers to temporary metadata. Global shader registration is appropriate for reusable pass templates, not an unbounded asset registry. A04, A05

Use logical HLSL register spaces and the backend's binding convention. The current Vulkan backend shifts texture/sampler/constant/UAV bindings and configures SPIR-V arguments; generated shared HLSL must not hardcode those final Vulkan binding numbers. Validate resource limits per target. A14

Generate HLSL declarations and uniform packing from one schema. Begin with deliberately explicit 16-byte slot packing for numeric parameters and a bounded resource list; record offsets/types, resource dimensions, stage visibility and register spaces. This trades a little storage for a simple first ABI. Do not memcpy arbitrary host structs containing Boolean or float3 fields into a cbuffer and assume matching layout.

Add focused DXIL/SPIR-V binding/layout inspection or compiler reflection at the compiler boundary, with GPU sentinel tests for the actual packing. This is new verification work, not an existing Arda reflection facility. Dynamic layouts can use retained metadata generated from the manifest, or a separate manifest-driven binder; either approach must satisfy the lifetime change below. A06

5.6 Cache keys, packages and runtime lifetime

Use separate identities:

  • Semantic graph key: schema/semantic version, executable graph, function dependencies, selected static values and effective settings. Ignore editor positions/comments. Parameter values read dynamically are not shader specialization inputs; package their defaults separately.
  • Program artifact key: graph key plus target/backend, compiler identity/options, material ABI, pass/geometry adapter version, generated source and transitive include contents, binding layout and relevant feature/quality flags.
  • Instance data key/version: effective dynamic values, texture bindings and dependency epochs. Pixel payload changes normally update texture content, not material shader code; resource type/decode changes can require revalidation or specialization.
  • Device/pipeline key: program/stages, layout, geometry format, render state, attachments/sample count and device ownership. Persistent native pipeline caches also require appropriate device/driver compatibility.

Use a collision-resistant content digest for the new material artifact store, and a manifest that verifies every expected file and digest. The existing backend's 64-bit FNV sidecar is not a replacement for a complete material package manifest. Include the compiler/semantic version in invalidation; never let a stale package silently survive a node semantic fix. A02, A05

The current compiler hashes broad frozen source manifests/include trees. Isolate generated job dependencies and add a regression where editing material A does not invalidate unrelated B. Updating a shared ABI include must invalidate both. Function changes invalidate only dependent graphs. A05

Proposed runtime objects:

  • FArdaMaterialProgram: immutable cooked code, binding schema, required capabilities and stable program identity.
  • FArdaMaterialInstance: values and textures referencing a program; updates publish a new version.
  • FArdaMaterialDeviceState: per-device shader/layout/pipeline objects and resource bindings.

For RDG, retain schema/program ownership in the graph's executable state or an equivalent lease that lasts through submission completion. Own the struct/member name storage and nested metadata as well as the top-level metadata object: the existing metadata contains raw character and nested-schema pointers. The existing static-metadata contract must be extended deliberately. Material textures, samplers, uniform buffers and dynamic uploads must be declared to RDG with the correct use; binding a descriptor does not establish a hazard edge. A texture override can require new graph resource declarations/bindings even while its program stays unchanged. A06, A07

Define the update protocol against RDG's frozen node descriptions: numeric changes use per-frame upload storage with producer/access dependencies; texture changes create a new binding/graph snapshot or a supported rebinding path that recomputes resource accesses. Include program/schema/resource versions in consuming node identity. Never overwrite uniform storage or descriptors still used by an in-flight frame. Material shader references may contribute pipeline stages, but physical resources must be declared and bound by the executable draw node: RDG rejects resource bindings on stage-only declarations. Reuse the existing generic pipeline contribution and graphics PSO facilities. A17, A18

Hot reload must create and validate a complete replacement program before publishing it. Keep the old program and resources alive until in-flight work retires. On compile failure, development keeps the last good program with an explicit error; an intentional error material is allowed for missing assets. Shipping loads prebuilt artifacts and reports missing/incompatible packages without requiring DXC or Unreal.

Custom HLSL deserves a separate boundary: Unreal custom expressions can have additional outputs, defines and include files, and their source often references Unreal shader symbols. Retain this metadata during export, but reject execution by default until a defined subset can compile against Arda's ABI. 8. Verification and success criteria

8.1 Build a semantic oracle, not just screenshot tests

Create small Unreal reference materials that isolate one behavior at a time. Render named material outputs into floating-point targets using a controlled reference harness, or encode selected values through a controlled unlit path. Capture the exact shader/translator, material settings, geometry, UVs, transforms, view and time. Instrumentation itself must preserve the property/stage semantics being tested; WPO needs a vertex test, not an emissive substitution.

Compare in this order:

  1. Serialized graph identity and effective parameter resolution.
  2. CPU-evaluable arithmetic/default/cast results where applicable.
  3. Generated shader compilation and binding/layout validation.
  4. GPU material attribute values with tone mapping/exposure/temporal effects controlled.
  5. Coverage/deformation across passes.
  6. Final lighting images under a separately specified lighting contract.

Maintain absolute/relative tolerances by operation and output. A reasonable initial target for finite float32 arithmetic/attribute fixtures is abs <= 1e-5 + 1e-4 * abs(reference) away from singularities; this is a proposed test threshold to calibrate against actual compiler/backend results, not measured parity. Texture filtering, compression and derivative cases need their own documented thresholds. Handle NaN/Inf/domain behavior explicitly; do not relax a global image threshold to hide semantic errors.

Minimum regression corpus:

  • Scalar/vector casts, output swizzles, disconnected pins and attribute defaults.
  • Sine period, Power boundaries, If threshold, zero/negative arithmetic and compiler optimizations.
  • Nested functions, repeated call sites, missing function inputs, recursive dependencies.
  • Parent/static/base-property inheritance; static versus dynamic-branch switches; static pruning; layer/blend parameter collisions.
  • Texture sRGB/linear data, alpha, normal decoding, UV sets, mip chains and stage legality.
  • Dynamic value changes, texture swaps and collection/view/primitive dependency epochs.
  • Masked color/depth/shadow agreement; WPO current/previous state where supported.
  • Unsupported node/domain/service, invalid package, include path restrictions and corrupt artifacts.
  • Program A/B cache isolation, function dependency invalidation, deterministic cook and runtime without compiler.
  • Hot reload while graphs/submissions are alive; device teardown/recreation and failed replacement.

8.2 Planned commands and existing regressions

Use the repository's provisioned graphics SDK and a separate build directory. Once the proposed CMake targets exist, the expected focused workflow is:

cmake -S . -B build/material -C build/graphics-sdk/GraphicsSdk.cmake -DARDASHIR_BUILD_TESTS=ON
cmake --build build/material --config Debug --target ArdaMaterialTests ArdaMaterialRuntimeTests
ctest --test-dir build/material -C Debug -R "ArdaMaterial" --output-on-failure

The two material test targets and matching GTest suite names are to be introduced. The SDK cache path must exist locally before using the example command. Add exporter commandlet invocation and preview capture commands to their own README when implemented; this research did not build Unreal or run such a commandlet.

Backend/RDG edits also require the relevant existing shader registration, source-directory, compiler/cache, parameter-binding and render-graph regression suites. Select test names from ctest -N in the configured build; do not assume a target name is a CTest test name. Run actual GPU checks on Vulkan and D3D12 where available and record capability skips distinctly. For this documentation change, validate the document and source anchors; rebuilding the engines would not validate the proposed design.

8.3 Measure costs before setting production budgets

Record cold/warm export and compile latency, reachable node/IR count, variant count, generated shader size, cache hits, uniform-update cost, shader instruction/resource usage, descriptor counts and draw/pipeline creation time. Include material/node identifiers in compile diagnostics and trace events without logging asset contents unnecessarily. Establish numeric budgets from the first representative corpus; no performance or coverage result has been measured by this plan.
