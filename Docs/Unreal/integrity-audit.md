Questions and recovered answers from [scene-reference.md](scene-reference.md), [stage-functions.md](stage-functions.md) and [reference.md](reference.md):

1. **Integration boundary.** Copied export carries bytes/formats/dependencies; borrowed resources require a compatible device, leases, subresource ranges, fences and queue/state handoff. Neither supplies a portable Unreal material shader ABI.
2. **Geometry coverage.** Eighteen families cover static and instanced triangles, Nanite, skinning, spline/terrain, procedural/dynamic meshes, collections/caches, particles, hair, volumes, water, points, UI surfaces and plugin producers. Each has a conversion, approximation or unsupported-report policy; collision geometry is not automatically render geometry.
3. **Material behavior.** Domain, blend, shading-model and translucency-lighting enums are distinct. Aliases retain their source values. Parent/permutation/parameter resolution, WPO/PDO, coverage and Substrate closures require executable behavior or an explicit limited conversion; a few baked maps cannot reproduce arbitrary material graphs.
4. **Placements and bindings.** Shared geometry is separate from stable primitive/instance identity, current/previous transforms, section bindings, custom values and per-view/shadow/ray visibility flags. Mesh submission descriptors are not neutral serialized scene records.
5. **Resources.** Formats, pitch, mip/residency state, color interpretation, sampler and buffer-view contracts accompany data. Dynamic textures have producers; borrowing requires readiness and retirement synchronization.
6. **Coordinates and motion.** The adapter records axes/units, high-precision origins, tangent/winding and mirrored-scale policy. Motion needs previous evaluated deformation as well as previous camera matrices; cuts and incompatible histories trigger invalidation.
7. **Lighting and environment.** Preserve light shape/units, channels, sky/captures, baked-light decode/associations and atmosphere/media semantics. Choose imported baked/cached terms versus relighting to avoid double counting.
8. **Updates and fidelity.** Versioned snapshots/change batches handle add/remove, dirty categories, topology, streaming and origin changes. Report exact, converted, approximated, omitted and unavailable features with the affected object/feature and reason.
9. **Scene updates.** `FSceneRenderer::OnRenderBegin`, `FScene::Update` and `FGPUScene::{Update,UpdateInternal,UploadGeneral}` distinguish CPU ownership/setup from later shader consumption of uploaded tables.
10. **Visibility and Nanite repair.** View relevance/gather/draw setup precedes the relevant consumers. Nanite main cull/raster can use valid previous HZB, then conditionally build current HZB and recover rejected work; the chart has an explicit bypass when two-pass recovery is not active.
11. **Lumen representations.** Card Surface Cache material/lighting updates, reusable world-space Radiance Cache probes and view-dependent screen probes are separate. Named update, trace, filter and integration helpers identify their responsibilities.
12. **Tracing and hit lighting.** Software distance-field coverage and hardware triangle/AS preparation are separate alternatives. Screen traces cannot supply arbitrary off-screen geometry; hardware traversal does not imply Hit Lighting or an automatic software GDF trace afterward.
13. **Depth, VSM and late work.** Water/front-layer receiver depth supplies VSM marking. Conventional early-shadow scheduling is distinct. Late decal/AO/velocity work and the earlier async-dispatch site retain their conditional placement.
14. **Composition.** Earlier indirect/AO work at `DeferredShadingRenderer.cpp:3429` is separate from direct `RenderLights:3467`. Async indirect outputs and direct-lit scene color feed the regular indirect composite at `3518`, followed by reflection/sky composition.
15. **Media and post.** Water's underwater subset, ordinary translucency, cloud alternatives and final media composition remain distinct. Enabled diaphragm DOF precedes the selected TSR/TAA/third-party temporal upscaler; later motion blur/bloom and tone/output conversion follow their main-path positions.
16. **RDG execution.** Pass declaration differs from callback execution. `FRDGBuilder::Execute`, `CollectPassBarriers` and `ExecutePass` identify resource scheduling, prologue/callback/epilogue work and retained backing resources. CPU return does not prove GPU completion.
17. **Diagram meaning.** Arrows are selected control/data prerequisites, not exhaustive C++ call stacks or serial GPU timings. Inactive feature paths remain inspectable; configuration controls are illustrative.

8. Niagara separates float, half and integer GPU attribute streams and ID-to-index lookup; CPU and GPU simulation paths differ.
9. Sparse volumes use page-table/physical-tile textures; CPU sparse data and texture-reference wrappers prepare/manage those resources.
10. Groom strands, cards/mesh LODs and Nanite groom proxies use distinct representations; their resources do not all exist together.
11. Conventional Landscape, Nanite Landscape and static-mesh Landscape proxies occupy separate declared branches, with the section-info mixin retained.

13. Collision sphere/capsule data does not imply a persistent visible mesh. Debug geometry and `EPrimitiveType` draw topology are separate concepts.
14. Inherited storage profiles are explicitly base context, not verified subclass layouts. The lexical discovery includes runtime/plugins and optional/local/conditional definitions but discloses unsupported aliases/macros and build-configuration limits.
15. Pipeline dependencies still distinguish Nanite visibility from GBuffer material evaluation, cached Lumen scene lighting before the main base pass, later async gather/reflections, direct lights and composition. Source call order and timeline spacing are not serial GPU timings.

## Findings corrected before publication

1. **Conditional C++ bases were malformed.** Preprocessor directives had leaked into base names for RHI validation mixins, disconnecting core inheritance. The extractor now separates type names from per-base conditions. `FRHIBuffer`/`FRHITexture` resolve `FRHIViewableResource`; `FRHIUniformBuffer` resolves `FRHIResource`. Their validation mixins are explicitly conditional. The retest found zero base names containing preprocessor directives.
2. **Some source anchors selected an earlier helper/custom path.** Main frame anchors now explicitly identify the main `RenderBasePass` call at `DeferredShadingRenderer.cpp:3059`, after Lumen scene lighting at 3041. Depth, Nanite main/post culling, shadow rendering, decal variants, atmosphere, water and translucency anchors were also corrected. Regeneration rejects moved pinned anchors.
3. **Early producers were present only in prose.** Added `atmosphere-luts` and `receiver-depth` nodes and dependencies. Early atmosphere inputs feed Lumen scene lighting; water/front-layer receiver depth feeds VSM requests. Final sky/water/translucency color composition remains separate.
4. **Conventional shadows retained VSM-only dependencies in the diagram.** The alternative now removes receiver-page-marking prerequisites from the arrows and inspector, and disables the VSM receiver-setup node. The diagram continues to show a late conventional-shadow scheduling window; it does not pretend to simulate every early-shadow configuration.
5. **Lexical false positives needed regression coverage.** Macro-definition templates and scoped enum declarations are now excluded from the class/struct inventory. Shader-parameter declarations retain namespace/enclosing-class qualification. The guided hierarchy also includes `Nanite::FSceneProxyBase` to expose the complete core proxy chain.

## Exam questions and answer assessment

These are concise records of the subagent's answers, not a verbatim transcript. Source line numbers cited here are those recorded in the docs; the subagent did not inspect engine files.

1. **Trace a static-mesh component to conventional and Nanite work; distinguish associations from inheritance.** Supported. Actor/component/asset ownership leads through a primitive proxy, `FPrimitiveSceneInfo` and GPU Scene. Conventional mesh batches become draw commands; Nanite resources feed visibility and material-shading bins. The answer distinguished both paths from the C++ base chain. Evidence: ownership FAQ; `scene-update`, `views`, `streaming`, `nanite-visibility`, `gbuffer`.
2. **Which management objects are CPU-side and which data live on the GPU? How do lifetimes differ?** Supported. UObjects, proxies, render-resource/RHI wrappers and RDG objects manage uploaded/generated GPU data. Graph handles, persistent backing resources and in-flight GPU lifetime are distinct. Evidence: “Three lifetimes”; CPU/GPU and RDG-history FAQs; `FRenderResource`, `FRHIResource`, `FRDGTexture`.
3. **What are the actual bases of `FSceneViewState`, and how does it differ from `FSceneView`/`FViewInfo`?** Supported. Its bases are `FSceneViewStateInterface` and `FRenderResource`. `FViewInfo` extends `FSceneView` for frame work, while view state persists histories. Evidence: those exact type entries.
4. **What GPU Scene tables/identity operations are required, and what fails on removal or teleport?** Supported at responsibility level. Primitive/instance/payload/light-related data need IDs, updates, upload dependencies, previous transforms and safe retirement. Stale IDs and invalid velocities/history are failure cases. The answer correctly marked the exact allocator and teleport policy as unspecified; generation counters are a proposed implementation choice. Evidence: GPU Scene group; `scene-update`.
5. **Explain previous-HZB main culling, current-HZB repair, disabled two-pass cases and disocclusion tests.** Supported. Retain rejected candidates, build current occlusion data, retest/rasterize recovered geometry, and disable two-pass when previous HZB is unusable. Moving an occluder must expose geometry in the same frame. Evidence: `nanite-visibility`.
6. **Does Nanite replace material/base-pass shading?** Supported: no. Visibility/depth identify geometry; later shading bins/material evaluation populate GBuffer or Substrate data alongside conventional draws. Evidence: “Nanite is geometry visibility”; `gbuffer`.
7. **Distinguish Surface Cache, Radiance Cache and screen probes.** Supported. Cards parameterize surfaces and store captured materials/cached lighting; world-space radiance probes provide reusable lighting; view-dependent screen probes gather and integrate visible-surface indirect light. Evidence: “Two Lumen caches”; `lumen-scene`, `lumen-lighting`, `gi`.
8. **Place Lumen scene lighting, base pass, async gather, direct lights and composition.** Supported after anchor correction. Recorded main-file anchors are 3041 → 3059 → 3248 → 3467 → 3523, with deferred reflection/sky composition at 3528. The answer distinguished declaration/dependency order from serial GPU timing. Evidence: `lumen-lighting`, `gbuffer`, `decals-ao`, `direct`, `composite`.
9. **Describe screen tracing and software/hardware fallback; does hardware completion trace the global SDF?** Supported. Unresolved screen work uses the selected representation. Hardware mode still completes cache/sky work but does not automatically run software GDF sphere tracing in that phase. Evidence: `trace-scene`, `gi`.
10. **Does hardware tracing force Hit Lighting, and why can Nanite/ray geometry disagree?** Supported. Traversal representation and hit shading are separate choices. Fallback geometry can differ from primary Nanite visibility; native Nanite ray tracing is separately enabled. Evidence: tracing/lighting and representation-mismatch contracts; `reflections`.
11. **Compare reflection reconstruction with diffuse final gather.** Supported at algorithm-stage level. Specular pixel/tile rays resolve with temporal/spatial filtering; screen/radiance probes gather/integrate diffuse and rough-specular lighting. Exact sampling distributions/filter equations are unspecified. Evidence: `gi`, `reflections`, `composite`.
12. **Can VSM run in the conventional early-shadow slot? What are its prerequisites and cache operations?** Supported. No in the documented path; receiver-depth inputs precede requests, then allocation/reuse/invalidation and dirty-page caster rasterization. The retest confirmed explicit early receiver nodes and the conventional alternative's different prerequisites. Evidence: `receiver-depth`, `shadows`.
13. **Where do decals/velocity fit, and why is one serial slot misleading?** Supported. DBuffer affects base-pass materials; later decals have conditional placement, including earlier preparation for stochastic lighting. Velocity can be in depth, base or later work. Evidence: `depth`, `gbuffer`, `decals-ao`.
14. **What remains when Nanite/Lumen are disabled? Are GI/reflection switches coupled in Unreal?** Supported. Conventional geometry and direct lighting remain. Missing indirect/specular methods need alternatives or their contributions are omitted. Unreal selects GI/reflection methods independently; the combined explorer switch is a documented simplification. Evidence: `reflections` caveat and configuration explanations.
15. **Explain atmosphere/water/translucency ordering and opaque-path limitations.** Supported at architecture level. LUT/receiver setup occurs earlier than final color composition; underwater/front-layer/separate-translucency paths have different placement. Transparent shading needs its own blend/refraction/lighting/depth policies. Full blend equations and every branch are unspecified. Evidence: `atmosphere-luts`, `receiver-depth`, `atmosphere`, `translucency`.
16. **What does TSR consume/produce and which histories need invalidation?** Supported at responsibility level. Current color/depth/velocity, jitter, prior history and output rectangles drive temporal reconstruction. Camera cuts, disocclusion, resolution/method changes and motion errors require rejection/reset handling. TSR does not generate geometry or GI. Evidence: `post`; temporal contract.
17. **When does RDG execute, how do histories survive, and where is presentation?** Supported. Earlier code declares graph work; graph compilation/execution resolves lifetimes/barriers/queues. Extract backing resources and import them next frame. Presentation is outside `FDeferredShadingSceneRenderer::Render`. Evidence: `execute`; RDG-history FAQ.
18. **Give a phased implementation plan with GPU operations and correctness gates.** Supported. The answer reconstructed conventional correctness, GPU-driven scene data, virtualized geometry, cached indirect light, scalable shadow/composition, then reconstruction/overlap. It correctly labeled these proposed work, not existing Ardashir features. Evidence: roadmap and stage checklists.
19. **Can the docs supply exact shader ABIs, timings and every plugin type? State coverage and ambiguous-base handling.** Supported, with explicit limits. The final counts and metadata agree. The index excludes enums, macro templates, plugins/editor/developer types and other listed forms; it is lexical. Ambiguous/unparsed bases and conditional mixins remain explicit. No exact production ABI/performance claim is made. Evidence: scope, catalog/manifest, type inspector.
20. **What prevents implementation from these docs alone?** Correctly identified limits: production field packing/formats, shader math, complete access/barrier examples, Nanite encoding/raster rules, Lumen sampling/filter thresholds and numerical reference fixtures. The atlas supplies architecture and an operation plan, not a binary-compatible port specification. These remain disclosed scope boundaries.
