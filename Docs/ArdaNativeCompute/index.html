ArdaNativeCompute

Register an operation with a native GPU kernel, a shader implementation, or both. Prepare one route for your device, queue, and resource bindings.

Choose an implementation route

Use the registry when a native kernel and a shader can implement the same operation. The caller supplies the same resource bindings and parameter bytes whichever route the device supports.

Link the module

Link your target against Ardashir::ArdaNativeCompute and include ArdaNativeCompute.h. Use CUDA/ArdaNativeCudaProvider.h for CUDA and CiG, or NVAPI/ArdaNativeNvapiProvider.h for D3D12 shader intrinsics. Choose a GPU provider.

Prepare and record an invocation

Register an FArdaNativeOperandDesc with ordered resource slots, an exact parameter byte count, and at least one implementation. Native variants have a source and can select launch geometry from the input. A shader fallback records equivalent work through the rendering hardware interface.

Supply the bound resources to Prepare. The registry checks resource types and ranges, then tries eligible implementations before it records any GPU work. The returned FArdaNativeComputePlan holds the selected work for its device and queue. Record it on an open command list or integrate it with a graph node.

A native provider reports whether it can access each view directly or needs an explicit conversion pass. For direct access, its FArdaNativeResourceHandoff also supplies the required graphics state. A scheduler can pass a FArdaNativeRouteCheck to reject a route that conflicts with the pass before preparation begins.

See both routes in use

Follow the native compute guide for linked CUDA kernels, module images, CUDA C++ source, shader fallback, and graph recording. Pixel Sort selects a CUDA surface route or an HLSL shader before the graph allocates its intermediate textures. For native work specific to your graphics backend, use the backend-defined operation hook.
