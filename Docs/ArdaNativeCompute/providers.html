Choose a GPU provider

An operand can offer several implementations of the same operation. Link the provider modules your application can use, then put the preferred implementation first in the operand.

Match the kernel to its execution path

ProviderGraphics backend and queueKernel and resource bindings
nvapiD3D12 graphics or computeDXIL compiled with NVIDIA HLSL shader intrinsics. Uses D3D12 shader views directly.
cuda-in-graphicsD3D12 graphics, or Vulkan graphics or computeCUDA kernels or qualified library calls on a device initialized for CUDA in Graphics (CiG). Resources must expose the required CUDA representations.
cudaQualified graphics backend and queue, subject to the device’s CUDA launch modeLinked CUDA kernels, PTX, cubin, CUDA C++ or library calls. Accepts an ordinary CUDA context.

List equivalent compute and graphics shader implementations in mShaderFallbacks in preference order. The registry tries them after the native variants. Use a packaged artifact to ship compiled code or explicitly select runtime compilation for source.

Link provider modules

The process-wide registry registers the providers linked into Ardashir::ArdaBackend. To use the same providers from a local registry, call RegisterLinkedArdaNativeComputeProviders(registry) and check its status. The built-in CUDA, CiG, and NVAPI modules are selected by ARDASHIR_NATIVE_COMPUTE_CUDA, ARDASHIR_NATIVE_COMPUTE_CIG, and ARDASHIR_NATIVE_COMPUTE_NVAPI. Each defaults to ON. ARDASHIR_ENABLE_CUDA enables the CUDA interop implementation in the built-in graphics backends and lets the build discover optional NVRTC support.

Implement IArdaNativeComputeProvider to advertise a provider ID, source formats and supported resource categories, probe the device, and prepare work. Report known slot states through GetRequiredState for preflight. Implement LoadKernel to decode your packaged format and RecordBatch to record a context-switching session. Supply a function in the arda namespace that calls RegisterProvider.

namespace arda
{
    FArdaRHIStatus RegisterExampleNativeProvider(FArdaNativeComputeRegistry& registry)
    {
        static const auto provider = eastl::make_shared<FExampleNativeProvider>();
        return registry.RegisterProvider(provider);
    }
}

Declare the static library target before configuring the Ardashir subdirectory. CMake references the registration function from ArdaBackend so the provider is pulled in when a consumer links the backend.

add_library(ExampleNativeProvider STATIC ExampleNativeProvider.cpp)
list(APPEND ARDASHIR_NATIVE_COMPUTE_MODULE_TARGETS ExampleNativeProvider)
list(APPEND ARDASHIR_NATIVE_COMPUTE_REGISTRATION_FUNCTIONS RegisterExampleNativeProvider)
add_subdirectory(path/to/Ardashir)
target_link_libraries(ExampleNativeProvider PRIVATE Ardashir::ArdaBackend)
target_link_libraries(MyApp PRIVATE Ardashir::ArdaBackend)

Build and deploy a kernel library

Each .ardakernels file contains one library and an index of payloads. A kernel key specifies library, provider, kernel name, and signature. Change the signature when the layout or binding contract changes, and use the same four fields in the packaged operand or graph reference. This manifest packages the NVAPI shader used in the next example.

{
  "library": "examples",
  "kernels": [{
    "provider": "nvapi",
    "name": "lane",
    "signature": "lane-v1",
    "format": "nvapi-dxil",
    "entryPoint": "WriteLane",
    "attributes": [0, 1, 8],
    "file": "@LaneDxil@"
  }]
}

After adding the Ardashir subdirectory, declare the build-time compiler command and point the packaging target at kernels.json.in. List include files that should trigger recompilation in DEPENDS. The library rebuilds when the configured manifest, a payload, or the packager changes. DEPLOY_TO stages the package beside its executable.

set(LaneDxil "${CMAKE_CURRENT_BINARY_DIR}/lane.dxil")
ardashir_compile_native_kernel(
    SOURCE lane.hlsl OUTPUT "${LaneDxil}" COMPILER "${ARDASHIR_DXC_EXECUTABLE}"
    ARGUMENTS -T cs_6_0 -E WriteLane -I "${NVAPI_HEADERS}" -Fo @OUTPUT@ @SOURCE@
    DEPENDS "${NVAPI_HEADERS}/nvHLSLExtns.h" "${NVAPI_HEADERS}/nvHLSLExtnsInternal.h"
        "${NVAPI_HEADERS}/nvShaderExtnEnums.h")
ardashir_add_native_kernel_library(ExampleKernels
    MANIFEST kernels.json.in DEPLOY_TO MyApp)

For prebuilt artifacts, point file to the artifact using a path relative to the manifest or an absolute path. You can also pack a complete manifest outside CMake with python Scripts/BuildArdaNativeKernelLibrary.py --manifest kernels.json --output examples.ardakernels. The packager requires Python 3.8 or later.

  • For NVAPI, use nvapi-dxil and list the extension UAV slot, register space, and required opcode IDs in attributes.
  • For CUDA or CiG, use cubin or ptx and list architecture words as (computeCapability << 1) | exact. For example, 150 describes a virtual target of 75. Use nvcc --cubin for device-specific binaries and nvcc --ptx for driver finalization.
  • To opt into runtime compilation of a CUDA C++ payload, use format: "cuda-cpp" with mode: "jit". The selected provider needs NVRTC at runtime. A missing runtime compiler can leave a compiled variant or shader fallback eligible.

Keep the file named <library>.ardakernels. Add an asset directory with AddArdaNativeKernelDirectory for application-managed locations, or load a specific file with LoadArdaNativeKernelLibrary. Pass the key, argument layout, and operand description to MakeArdaPackagedNativeOperand, then register the result. The provider reads the payload during resolution and validates its arguments against the layout.

Bind an ordinary graphics allocation

The CUDA and NVAPI helpers install both operand boundary hooks. They bind a compatible view directly and stage copies when the provider needs another view. Choose the helper and the resource category that matches the kernel's ABI.

HelperNative resource categories
UseArdaNativeCudaResourcesArdaNativeCudaBufferCategory for linear buffers and ArdaNativeCudaSurfaceCategory for textures exposed as CUDA surfaces. Applies to CUDA and CiG.
UseArdaNativeNvapiResourcesArdaNativeNvapiRawBufferCategory for raw buffer views and ArdaNativeNvapiTextureCategory for texture views.

To write into an ordinary graphics buffer with the CUDA buffer-fill operand, use this setup after adding its native variants and before registering it. Create a device-local destination with Raw | UnorderedAccess usage and UnorderedAccess as its initial state. Pass the same output range to RunFill. Buffer-fill operand

UseArdaNativeCudaResources(fill);
for (auto& variant : fill.mVariants)
{
    variant.mNativeResources = fill.mResources;
    variant.mNativeResources.front().mCategory = ArdaNativeCudaBufferCategory;
    variant.mGraphicsStates = {EArdaRHIResourceState::UnorderedAccess};
}

The fill's write slot binds a CUDA-shared scratch range. The plan records the kernel, copies the written range back into the declared graphics range, and restores its state. Use ReadWrite to preserve bytes within a partially updated staging range. The native session flushes preceding work for graphics preparation commands and closes the current batch before recording graphics publication commands.

For a CUDA kernel authored to take linear texture data, declare a logical texture slot and a native buffer slot. Obtain the selected mip's row and slice pitches with GetArdaRHITextureBufferFootprint and supply them as kernel parameters. The built-in pitched helper handles one mip of a single-layer texture or a 3D region. Same-format texture staging copies the selected mip's layers. Use the operand hooks to define application-specific format conversions.

A multi-provider operand can select its conversion functions by context.mProvider.GetDesc().mId. The directional helpers are PrepareArdaCudaGraphicsToNative, PrepareArdaCudaNativeToGraphics, PrepareArdaNvapiGraphicsToNative, and PrepareArdaNvapiNativeToGraphics.

For provider-owned storage, declare EArdaRHIResourceType::Count on the native-side slot and its provider category. Set FArdaNativeResourceView::mNativeResource to an IArdaNativeResource with the matching provider and category IDs. The provider's Prepare and recording implementation must retain that allocation through GPU completion.

Run a CUDA kernel in graphics

Include CUDA/ArdaNativeCudaProvider.h. Add a linked or in-memory kernel with AddArdaNativeCudaVariants(operand, variant). Both variants share its source, argument layout and launch policy. For a package, publish an entry for each provider ID you want to support.

To require CiG, choose the graphics-queue CUDA mode when creating the device, then set context.mPreference = EArdaNativeComputePreference::NativeOnly and context.mRequiredProviderId = ArdaNativeCudaInGraphicsProviderId. A device using an ordinary CUDA context fails this check. With automatic routing, the registry tries the next eligible variant.

D3D12 CiG captures CUDA work directly on its graphics list. Vulkan CiG uses a context associated with the graphics device, submits separate CUDA segments, and orders them with graphics through semaphores. Qualify the actual buffer or texture as well as the device. A driver may support a shared linear buffer and reject a shared image. CUDA queues and resource handoffs

Use an NVAPI shader intrinsic on D3D12

This shader writes the lane index of each of 32 threads into a raw buffer. Reserve the extension UAV in a separate register space. Space zero holds the output.

#define NV_SHADER_EXTN_SLOT u0
#define NV_SHADER_EXTN_REGISTER_SPACE space1
#include "nvHLSLExtns.h"

RWByteAddressBuffer Output : register(u0, space0);

[numthreads(32, 1, 1)]
void WriteLane(uint index : SV_GroupIndex)
{
    Output.Store(4 * index, NvGetLaneId());
}

Save the shader as lane.hlsl and compile it from the repository root with DXC. Ship the resulting DXIL with the application.

dxc -T cs_6_0 -E WriteLane -I ThirdParty/NVAPI -Fo lane.dxil lane.hlsl

Load the DXIL from a kernel library or pass the bytes directly to the source factory. Declare the shader’s extension UAV slot, register space, and every required opcode. The provider queries the active D3D12 device for those opcodes and builds the compute pipeline through NVAPI.

#include "NVAPI/ArdaNativeNvapiProvider.h"
#include "nvShaderExtnEnums.h"  // Add ThirdParty/NVAPI to the shader author's include path.

using namespace arda;

FArdaRHIStatus RegisterLaneIndex(FArdaNativeComputeRegistry& registry,
    eastl::vector<uint8_t> dxil)
{
    FArdaNativeNvapiSourceDesc source;
    source.mDxil = eastl::move(dxil);
    source.mRequiredOpcodes = {NV_EXTN_OP_GET_LANE_ID};
    source.mExtensionUavSlot = 0;
    source.mExtensionRegisterSpace = 1;
    auto shader = CreateArdaNativeNvapiSource(eastl::move(source));
    if (!shader) return shader.mStatus;

    FArdaNativeOperand operand;
    operand.mId = "example.lane-index";
    FArdaNativeResourceSlotsCreator slots;
    slots.AddBuffer("Output", EArdaComputeAccess::Write);
    operand.mResources = slots.Finalize();
    UseArdaNativeDirectResources(operand);
    operand.mVariants.push_back({"lane-id", shader.mValue, {}});
    return registry.RegisterOperand(eastl::move(operand));
}

Bind a 128-byte buffer view with Raw | UnorderedAccess usage and prepare the operation for one group. DXIL fixes the block size and shared memory. Use mGridSize for group counts and leave the other launch fields at their defaults. On a raw RHI list, transition the output to UnorderedAccess and call CommitBarriers() before recording the plan. A graph pass declares the same write state so the scheduler can order the transition. Submit the recorded command list. Record and submit an invocation

For additional bindings, operand slot i maps to ti for reads and ui for writes in space zero. Buffer offsets and sizes must be multiples of four, and offsets must meet the device’s storage-buffer alignment. Texture views select a mip. The handoff state is NonPixelShaderResource for reads and UnorderedAccess for writes. Scalar parameters are packed as 32-bit constants at b0. The extension UAV uses one DWORD of the D3D12 root signature. The remaining 63 DWORDs cover resource tables and constants.

Check the selected implementation

QueryProviderSupport reports the cached device qualification, execution mode and runtime compilation availability. Use CheckSupport to test an operand and its kernel requirements before allocating provider-specific storage. Call Prepare with the final views, then inspect GetRoute() and GetVariantName(). A missing driver, opcode, or resource representation can send an operation to a shader fallback. Register a shader fallback
