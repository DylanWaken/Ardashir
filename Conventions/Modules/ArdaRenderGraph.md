# ArdaDependencyGraph coding conventions

These conventions apply to project-owned C++ types in `Source/ArdaInfra/ArdaDependencyGraph` and supplement the [repository conventions](../ArdaCodingConventions.md).

## Public names

Use the project-wide `Arda` stem with the applicable category prefix: `FArda` for classes and structs, `IArda` for interfaces, `EArda` for enums and `TArda` for templates. Examples include `FArdaDependencyGraph`, `FArdaInductor`, `EArdaDependencyAccess` and `TArdaNodeDefinition<Node, Parameters, EArdaNodeType::Compute>`. Public APIs describe persistent graph concepts; native recording implementation remains private.

## Node authoring

Compose operations using their resource values. Open an `FArdaGraphEdit` and obtain `FArdaGraphBuffer` or `FArdaGraphTexture` values by allocating, binding, or calling an operation that produces them. Pass those values to another operation or a node's named callable. Retain terminal resources with `Edit.Keep()`, then check the statuses from `Edit.Commit()` and `Graph.Compile()`. Call `Graph.Submit()` to record and submit work on the calling thread, then call `Graph.Wait(Ticket)` to retire it and publish readbacks.

Use the built-in `AllocateBuffer`, `AllocateTexture`, `BindBuffer`, `BindTexture`, `Clear`, `Upload`, `CopyTo`, `Clone`, and `Readback` operations where they apply. Pass typed resource values between operations so callers can compose them directly.

Give every node class its own parameter struct, including nodes with identical fields or no inputs. Do not reuse another node's parameter type, alias it, or pass a shared catch-all struct to multiple node classes. Include only that operation's inputs and outputs and use named fields instead of positional resource arrays. Shared immutable data may be referenced explicitly, while deliberately dynamic pointees need a documented synchronization contract. Each attached node instance retains a separate immutable parameter snapshot; edits to a caller's struct do not update attached nodes.

For exported device code, register an immutable `FArdaRuntimeNodeDesc` through `FArdaRuntimeNodeDefinition`. These data-authored definitions use one explicit ABI and `FArdaRuntimeNodeParameters`; they do not require a new C++ class per kernel. They lower to the same `FArdaDependencyNodeExecutable`, registry, resource accesses, compiler and CUDA sequence as class-authored nodes. Declare each pointer argument and its accessible buffer range, each scalar's exact bytes, the PTX/cubin target, and launch dimensions. Library registration validates all entries before publishing any. A registry name may only be reused for an identical definition; exported names must identify the compiled artifact as well as its entry point.

For native operations that can select a CUDA variant or an equivalent compute
shader, register the implementations and shared resource contract through
[ArdaNativeCompute](../../Docs/ArdaNativeCompute/index.html). Its CUDA provider
accepts linked entries, prebuilt PTX or cubin, and CUDA C++ for optional NVRTC
compilation during preparation. Use the graph integration to declare
dependencies and record the selected route.

Represent tensors with the Backend `FArdaRHITensorDesc` and a graph buffer in `FArdaGraphTensor`. Dimensions, element strides, dtype and byte origin are semantic identity. Use `ARDA_NODE_TENSOR` / `ARDA_COMPUTE_TENSOR` metadata for tensor parameters; resources remain ordinary buffers, and overlapping writable tensor elements are rejected. Tensor descriptors do not imply broadcasting, layout conversion or operator dispatch.

Load offline model descriptors with `FArdaGraphPackage::Load`, apply a separate named checkpoint through `LoadStateDict`, then record named tensor bindings through `Invoke(Edit, Bindings)`. Descriptors contain the subgraph recipe and state schema; checkpoints contain only tensor values. Exporters must externalize model state before optimization so weights cannot be folded into code. Loading validates the exact key set, dtype, shape and byte count atomically and returns a new immutable loaded instance. Record that instance in a new edit to change weights; existing invocations retain their snapshots. Commands expand into ordinary graph operations, preserving compiler order, including inside a typed subgraph's `Build` body. Weights and structural constants use `AllocateInitializedBuffer`: immutable host bytes initialize a persistent graph-owned buffer prefix once on first physical preparation. Compile and attachment submit no initialization work. Reused storage retains later writes; initialization is not a per-frame reset. A new physical allocation is uploaded and waited before it is published. Declare per-frame fills explicitly when required.

Publish every reusable node with `ARDA_DECLARE_GRAPH_NODE(FArdaMyNode, RunMyOperation);` immediately after its class declaration. Define the same pair once with `ARDA_DEFINE_GRAPH_NODE(FArdaMyNode, RunMyOperation);` in the owning implementation, in the same namespace. The named global const object is shared across translation units and retains no graph or execution state. Choose a callable name unique across `arda`; keep its C++ identity separate from the process-wide registry name in `GetMetadata`. Declaration automatically registers the named type without device setup, allowing deserialization before its first invocation. Direct calls and explicit `FArdaMyNode::Register()` also support idempotent registration. See the [complete registration walkthrough](../../Docs/ArdaRDG/registering-nodes.html).

Use the exported callable for direct composition: `RunMyOperation(Edit, Parameters)` or `RunMyOperation(Edit, Input, Output, Value)`. Positional arguments aggregate-initialize `FArdaParameters` in declaration order with perfect forwarding. The static `FArdaMyNode::Invoke` and generic `Edit.Invoke<FArdaMyNode>` entries support the same positional form. Prefer a parameter struct or initializer for many optional fields and diagnostic names. Obtain typed output variables with the returned operation's `GetBuffer(Slot)` / `GetTexture(Slot)` before committing or canceling the edit; typed variables may then live as long as their graph resource. Every invocation creates a fresh operation with an automatic diagnostic name and uses the normal registry, validation, resource declaration and preparation path. A node may expose domain-specific static functions that build its parameters, call inherited `Invoke`, and return typed outputs. One free function name may use resource-type overloads to select different node classes, as `CopyTo` does for all four buffer/texture source and destination combinations. Keep overloaded facade function names distinct from global callable object names. Keep registration and dependency declarations in the node definition; do not introduce a separate facade registry.

Use `Edit.Invoke<Node>(Parameters)` for generic typed code and
`Edit.Invoke(DefinitionName, Parameters)` for registered discovery. Both static and
typed invocation accept an initializer callback filling `Node::FArdaParameters`
and an optional diagnostic name. The callback runs synchronously and may return
`FArdaRHIStatus`; it must not retain the temporary reference or edit the graph.
Every call creates a fresh operation, and duplicate explicit names fail. Raw graph
mutation and node attachment are private implementation details.

Derive class-authored operations from `TArdaNodeDefinition<Derived, Parameters, EArdaNodeType::Type>` in `ArdaNodeDefinition.h`. Declare parameters with `ARDA_BEGIN_NODE_PARAMETER_STRUCT`, the node field macros and `ARDA_END_NODE_PARAMETER_STRUCT`. Plain parameter structs are rejected. Implement static `GetMetadata` and the domain's execution hook: `Record` for native work or `PrepareCuda` for CUDA sequences. Synchronization nodes may omit execution. The parameter schema supplies canonical keys and static dependencies; override `GetCanonicalKey` only for values without semantic encoders and `Describe` for pipeline contributions or dynamic effects. The base enforces this contract at compile time and owns invocation, registration, attachment, parameter retention and preparation lifetime. Do not duplicate or hide its invocation/attachment/registration methods in derived nodes.

Map GPU resources through `ARDA_NODE_SHADER_*` or `ARDA_NODE_CUDA_*` fields to the canonical shader or operand schema. Access direction, binding kind and shader visibility come from that schema, and compilation or CUDA preparation verifies coverage. Every graph shader must carry registered parameter metadata, including an explicit empty schema for parameterless shaders. For individual graphics and ray stages, declare logical connections through `ARDA_NODE_STAGE_INPUT` or `ARDA_NODE_STAGE_INPUTS`; the compiler assembles pipelines from these typed values. CUDA nodes resolve declared fields through `ResolveNodeCudaParameters` before appending their prepared dispatches.

Keep shader registration, binding metadata, layout creation and fixed pipeline configuration inside each node's implementation. Declare an opaque nested `FArdaState` and implement `Prepare(Device)` for immutable setup shared by live instances on that device. Declare `FArdaInstanceState` and implement `CreateInstance(Device, Parameters, State)` for private mutable bindings or parameter-dependent setup. Defaults handle nodes without setup. Validate inputs through `Validate`; return failures and never submit GPU work from attachment hooks. Device state is weakly cached by the base and strongly retained only by live bound instances. Shared state must be immutable; different nodes may record concurrently.

Declare required backend and environment features through `GetRequirements(Parameters)` and query inherited `CheckRequiredFeatures(Device, Parameters)` for a read-only preflight. Return and propagate `FArdaRHIStatus`; do not treat an unavailable capability as supported. Attachment checks requirements before setup, and the compiler's required-features rule rechecks the environment, including cached revisions and custom rule pipelines. Requirement selectors and environment predicates must be deterministic, read-only, and safe to evaluate repeatedly. Descriptor inference supplements explicit declarations; it cannot discover hidden shader instructions or external-library needs.

A CUDA node may optionally implement `RecordComputeAlternative(Context, Parameters, State, Instance)` with the ordinary native recording signature. The framework selects it before preparation when the device has no qualified CUDA mode, and lowers the invocation to a compute node without CUDA batches or interop allocation requirements. Use `UsesComputeAlternative(Device.Get())` in shared `Prepare` to construct the appropriate state; describe the selected pipeline through that state. During `DeclareResources`, use the borrowed `Context.GetDevice()` pointer to select resource flags such as `mbCudaInterop`; the framework preserves explicitly requested flags. The independent `GetComputeAlternativeRequirements(Parameters)` list defaults to empty; repeat common requirements in both route lists. Both routes must implement the same public operation and declare all resource effects. Do not invoke CUDA APIs or resolve CUDA-native operands in the compute recording hook. Without available CUDA and an authored alternative, invocation returns `Unsupported`. Do not switch routes after recording/submission failure or silently remove a user's feature requirements.

Encode semantic values and full resource identities in canonical keys without structure padding. Derive accesses, pipelines, cost and workspace from the same frozen parameters. Keep semantic pointees immutable; document deliberately dynamic inputs and their synchronization contract. Registry discovery uses `Edit.Invoke` with the registered public parameter schema; prepared execution state remains private.

Declare every resource access with its direction and precise byte or texture-subresource range. A region with one producing node keeps attachment-independent producer-to-reader ordering. When two or more distinct nodes write the same region, attach its operations in their intended execution order: overlapping writes and intervening reads follow original successful attachment order. A read observes the preceding write; an owned read before the first write fails, while an import may supply initial contents. Disjoint regions remain independent. Repeated writes reuse the same logical handle and physical graph resource; declare separate outputs when older values must remain available.

Operation call order determines repeated-write semantics; cancellation restores
the starting construction. Use `Edit.Order(Producer, Consumer)` for effects that
resources do not describe. These constraints cannot contradict resource hazards. Record through `FArdaDependencyExecutionContext`, resolve only declared resources and propagate RHI failures. Supply stages and settings for automatic pipeline inference instead of hiding manual native PSO creation inside ordinary graph operations.

## Edits and execution

Use `EArdaNodeType::Subgraph` for a named operation whose implementation is another graph. Declare its interface through the ordinary parameter schema and `DeclareResources`, then implement `Build(FArdaSubgraphContext&, const FArdaParameters&)`. Record the body through `Context.GetEdit()`, request declared inputs by their parameter names, and publish every output with `Context.DeclareOutput`. `FArdaExpandSubgraphsRule` runs Build recursively as the first default preprocessing rule, before stage assembly and dependency analysis. Keep expansion in the preprocessing rule layer; custom programs must eliminate all subgraph nodes before compile rules run. Its edit belongs to the preprocessor: do not commit, cancel, or change global compiler options from the body. Internal explicit names are scoped to the parent instance. Publish compatible transient storage or write the predeclared parent output directly; undeclared accesses and missing outputs fail preprocessing.

Graphs own semantic node descriptions, public parameters, connections and optimization/culling metadata. `FArdaPreprocessor::Preprocess(const Graph&)` returns an editable normal graph; `FArdaInductor::Compile(const Graph&)` requires that preprocessed graph and returns a separate result without modifying it. Keep prepared parameter wrappers, native binding layouts, allocations, runtime and telemetry in `FArdaInductorCompileResult`. Use `TArdaGraphPreprocessRule` in `Inductor/Preprocess` for graph transforms and `TArdaGraphCompileRule` in `Inductor/Compiler` for result transforms. Insert registered nodes through the preprocess view's `Edit` callback. `FArdaGraphExecutor` owns execution independently of source graph lifetime. Use `Graph.Serialize()` / `Deserialize()` and `Save()` / `Load()`; file access must delegate to backend shared helpers. Archives preserve graph state, registered node/rule schemas, parameters, options and connections. Native resources and opaque values persist as named typed slots and must be rebound before compilation; never serialize process addresses or padding.

Graph archive version 4 preserves resource revision declarations and committed edit membership alongside portable definitions and buffer initializer bytes; versions 2 and 3 remain readable. Deserialization validates the complete archive before publishing runtime definitions, while class-authored definitions still require registration. The `.ardagpu` version-two descriptor carries static compiler output and typed state slots; `.ardastate` version-one checkpoints carry named dense tensors. Legacy version-one `.ardagpu` snapshots remain readable. Export scripts live in `Tools/ModelExport`; unsupported host control flow, external library dependencies or unverified launch contracts must fail export. PTX compatibility is bounded by the target GPU and driver, and cubins require their declared architecture.

Restrict mutations to explicit edit transactions. Use the scoped `FArdaGraphEdit` facade exclusively: construction begins the transaction, `Commit()` checks authoring failures and queues the closed edit, and `Cancel()` or destruction discards an uncommitted transaction. Preserve the first authoring failure in the edit and stop subsequent facade mutations; programs can check one commit result without accepting a partially authored graph. Resource handles must remain generation-checked across cancellation, removal, revision changes and slot reuse.

Record each frame through edit scopes and commit them before compilation. `Compile()` selects a cached persistent revision or compiles a new one on the calling thread. A successful compilation locks the construction until a submission or execution attempt. A new construction starts empty. Repeated execution reuses the selected revision.

`Submit()` records native commands on the caller and returns a GPU frame ticket. Use `Graph.IsComplete(Ticket)` to poll or `Graph.Wait(Ticket)` to retire the frame and publish readbacks. `Execute()` includes retirement. When one graph consumes another graph's GPU output, retire the producer's ticket before submitting the consumer, or use explicit native synchronization with the required resource states and ownership transfers. Applications control the order of independent graph calls.

Independent host threads may open private edits. Exclude concurrent publication when borrowing topology, options or compile results, and reacquire those references after revision changes.

Keep revision identity sensitive to edit order, semantic node parameters, resource descriptors and imported native identities. Preserve canonical equality checks and retained pointee lifetime; an address or hash alone must not hide a semantic change. Expose cache invalidation and forced compilation without forcing callers to remove nodes. Failed compilation retains queued work for another correction edit or `DiscardPendingEdits()`.
