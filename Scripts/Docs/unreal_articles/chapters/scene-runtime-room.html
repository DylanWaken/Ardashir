Make the architecture concrete in a real Unreal room

The courtyard introduces why the abstractions exist. Now we can inspect a smaller scene rendered by the actual engine. This is the same indoor room used in the Lumen essay: four meters wide, five meters deep, three meters high, open toward the camera, with a red wall, a green wall, a matte block, a glossy block, and one rectangular ceiling light. It was constructed and rendered in the local Unreal 5.8.1 editor on an RTX PRO 6000 Blackwell using DX12 and Shader Model 6. The following images are captures of Unreal's renderer. They are not the earlier illustrative software courtyard.

Seven visible static-mesh components make the room: five enclosing surfaces and two blocks. All seven refer to /Engine/BasicShapes/Cube.Cube. There are seven placements and one shared mesh asset, with five material assets. The floor, ceiling and back wall share the neutral material. This is an unusually useful example because the relationship is measurable: duplicating a box-shaped object does not require duplicating the cube's vertex buffer. Each component supplies its own placement and material binding.

The authoring script creates a StaticMeshActor, obtains its StaticMeshComponent, calls set_static_mesh with the shared cube, assigns a material, and sets the actor's scale and location. Those are public authoring operations. When the component registers, the render-state lifecycle described in the previous chapter creates the rendering representation. The script does not directly allocate an FPrimitiveSceneInfo, write GPU Scene buffers, or create draw commands. Those are consequences of registration and renderer processing.

The CPU lighting lab describes coordinates in meters. Its layout maps to Unreal centimeters as \((x_u,y_u,z_u)=(-100x,100y,100z)\). The sign on X keeps the red wall on the same screen side under the chosen Unreal camera orientation. Follow the matte block. Its cube begins at local coordinates bounded by ±50 cm. With no rotation, its world transform is \(p_w=t+Sp_l\), where \(t=(77.5,285,52.5)\) cm and \(S=\operatorname{diag}(0.95,1.1,1.05)\). The local corner \((50,50,50)\) becomes \((125,340,105)\) cm. The opposite corner becomes \((30,230,0)\). Those values explain its actual bounds and floor contact. The shared cube asset never changes to contain those world coordinates.

For a general rotation and scale matrix \(A\), a local axis-aligned box with center \(c\) and half-extents \(e\) transforms to a conservative world axis-aligned box with center \(Ac+t\) and half-extents \(|A|e\), where absolute value is elementwise. To derive this, write every local point as \(c+\delta\) with \(|\delta_j|\le e_j\). Then each world-axis deviation obeys

\[|(A\delta)_i|=\left|\sum_j A_{ij}\delta_j\right|\le\sum_j|A_{ij}|e_j.\]

The bound is attained at a box corner for each axis, so it is the exact AABB of the transformed box. It is still only a bound on the mesh. This distinction becomes critical for rotated thin objects and for deformation that extends beyond the asset's original box.

Inspect the room as geometry and view-dependent work

The lit image hides both the simplicity of the source geometry and the hierarchy of decisions that makes it visible. Switch the same camera to wireframe. The enclosing walls and the blocks are transformed instances of a cube; they do not become complex geometry merely because indirect light produces detailed gradients on their surfaces. A material, a lighting cache, and a depth discontinuity can create image detail without adding vertices.

Now display bounds. The renderer can reject a component's bound without visiting every triangle. If the bound intersects the view, that is permission to do more work, not proof that all its triangles are visible. The matte block can hide part of the back wall even while both component bounds are inside the camera. A shadow view has different visibility from this camera. The bounds overlay makes the culling input visible; it is not a visualization of every internal culling decision or a measurement of draw count.

The chain to remember is component → proxy behavior → scene membership → GPU-addressable placement → view work. The component owns editable state. The proxy presents a rendering snapshot and geometry-specific behavior. Scene info associates it with the renderer's persistent organization. GPU Scene makes needed data accessible to shaders. The view chooses relevant work. None of these transitions means that the seven UStaticMeshComponent objects are copied byte-for-byte into a GPU buffer.

A depth image is a useful next checkpoint because it contains the result of visible-surface selection without the full lighting solution. The front of the matte block wins where it overlaps the back wall; the back wall remains represented elsewhere. The stored depth convention and the debug view's display mapping are separate matters. For this capture, a native post-process material reads linear SceneDepth in centimeters and divides by 1,000 after tone mapping. Its shader output reaches white at ten meters. This readable display is a custom diagnostic of the actual depth buffer, not raw device Z; do not confuse it with the engine's default depth-view scale.

For Arda, the corresponding debugging feature should expose both levels: human-readable overlays and machine-readable records with units. A bounding-box screenshot answers whether placement is plausible. A bounds export can verify exact values. A depth visualization reveals discontinuities; an untonemapped depth export supports numerical comparisons. Keeping these forms together makes the scene system testable without confusing a display transform with the underlying data.

Separate the room's surfaces from the light they reflect

The same seven components produce several useful per-pixel descriptions. First examine base color. It answers what material property the winning surface supplies, before indirect illumination makes the neutral floor appear tinted. The red wall's material and the red light reflected onto the floor are different quantities. The floor keeps its neutral base color even where its final lit appearance becomes red. This is the concrete reason deferred rendering separates surface evaluation from lighting evaluation.

The world-normal view answers a different question: which way does the visible surface face? Identical materials on the floor and back wall do not imply identical illumination, because their normals differ. Under nonuniform scale, transform normals with the inverse transpose of the linear transform and normalize them. The derivation follows from perpendicularity. For a tangent \(v\), \(n^Tv=0\). After transforming the tangent to \(Av\), choose \(n'=A^{-T}n\), giving \((n')^TAv=n^Tv=0\). Multiplying a normal by \(A\) as if it were a position does not preserve this relation for general nonuniform scale.

The matte block uses roughness 0.7 and metallic 0; the glossy block uses roughness 0.12 and metallic 0.85. Roughness changes the distribution of reflection directions, while metallic changes how base color and reflectance participate in the shading model. These values are shader inputs, not labels such as “reflective object” stored on the actor. A low-roughness surface requires sharper directional information from the reflection system than a rough diffuse surface does.

These views are selections of shading inputs, not an exhaustive description of the engine's packed GBuffer layout. The layout can depend on material features and renderer settings. What survives those implementation choices is the contract: visible-surface evaluation makes material properties available, and lighting uses them with positions, normals, light data, shadows, and indirect-light estimates. The light component is not another material slot on each wall. It contributes illumination to relevant receivers through renderer light data and lighting passes.

The ceiling light in this capture is a movable RectLightComponent with 2,400 lumens, source width 130 cm, source height 120 cm, and attenuation radius 2,000 cm. It is placed at (0,270,298) cm and points downward. Exposure is held fixed for the capture sequence. These settings make the experiment reproducible, but the image is not a radiometric comparison with the CPU lab: the reduced renderer uses its own normalized radiance units, while Unreal applies its light-unit conventions, shading, reconstruction, exposure, and display pipeline.

Change one room and follow the representations that must respond

Move the matte block while keeping its mesh and material. The capture script changes its mobility to movable and translates it by (−100,−80,0) cm. Its center moves from (77.5,285,52.5) to (−22.5,205,52.5). There is still one shared cube asset and the same material binding. Placement, bounds, visibility, shadows, tracing instances and affected lighting history must respond. This is why “the mesh changed” is an insufficient update message.

Now change only the light's intensity and color, leaving the moved block in place. The light becomes 7,200 lumens with linear RGB (1,0.55,0.25). The cube geometry and material base colors remain unchanged. Direct lighting changes immediately when the new light data is consumed; indirect illumination and histories need their own update policies. A material recapture is not inherently required merely because a light changed. Cached illumination is the affected quantity.

Return to the original room's tracing and caching views. Lumen's mesh distance fields describe geometric proximity for software tracing. Its cards parameterize surfaces for material and lighting storage. These two views answer different questions about the same seven components. A card is not a triangle acceleration structure. A distance field is not a material texture. A valid component transform must place both consistently, but their resolution, update mechanism, and failure modes differ.

This room connects the full architecture. Authoring objects provide semantic identity and editable values. Proxies and scene info organize renderer-owned behavior and membership. GPU records provide compact placement and material access. View passes resolve surfaces. Deferred shading consumes their properties. Lumen maintains additional geometry and radiance representations so light can arrive from surfaces beyond the camera's first hit. The independent Lumen walkthrough follows those caches numerically and visually; the present lesson is that a scene architecture must let each consumer maintain its own representation without losing track of which object and revision it describes.

The reproducibility bundle contains the room creation script, a small project-local editor bridge for verified viewport modes, engine configuration, exported scene inventory, capture commands, and image hashes. Internal proxy addresses, primitive packed indices and draw counts were not instrumented in this experiment, so the essay does not infer them from actor labels. For a future Arda implementation, expose these identities explicitly with generations and revision numbers. That would allow a trace to follow this very block from authoring edit to upload, draw, tracing update and lighting invalidation without relying on a screenshot to guess the transition.
